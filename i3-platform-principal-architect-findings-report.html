Summary: The i3 platform demonstrates sophisticated architectural intent: a governed, multi-tenant, event-driven agentic AI platform with 17 namespaces, a polyglot runtime (Python/TypeScript/Go), and a well-documented hard-constraint framework (HC-1 through HC-8). The IBM Bob integration guide provides an unusually rigorous AI-assisted engineering protocol. However, three systemic risks require immediate attention before the next customer commitments: (1) 306 uncommitted changes sit on main creating a release integrity gap; (2) several commercial capability claims exceed current infrastructure reality; and (3) critical Phase 1 security and tenancy remediation work is still in-flight. The modernisation roadmap is sound and should be executed in strict phase order.

Any customer-facing claim about GPU-accelerated inference is currently inaccurate.

2. IBM Bob Technical Implementation Guide — Assessment

2.1 Document Quality

The i3-IBM-Bob-Technical-Implementation-Guide.md is an exceptionally well-structured 1,080-line engineering contract. It consolidates four source documents into a single authoritative reference covering hard constraints, engineering principles, the 4-phase Explore→Plan→Implement→Verify cycle, a risk-tier model (Tiers 0–4), a Master System Prompt, and a 10-point Definition of Done. This is best-in-class for AI-assisted engineering governance.

2.2 What Works Well

  • Hard constraint enforcement: HC-1 through HC-8 are correctly reflected in .bob/rules/01-hard-constraints.md and enforced on every Bob session.
  • Risk-tier model: The 5-tier agent autonomy model (Read → Low-risk → Medium → High-risk → Destructive) with explicit approval gates aligns with HC-3 and HC-5 requirements.
  • Capability Claim Matrix: The document introduces a structured test for when claims may be made (GPU acceleration, regional residency, per-tenant metering), protecting against premature commercialisation. This should be shared with the sales team.
  • Phase gates: The EXPLORE-GATE.md → PLN deliverables → IMP checklists → VER red-team structure prevents architectural drift.
  • Master System Prompt: The 20 mandatory Bob behaviours are well-scoped and machine-enforceable.

2.3 Gaps Identified

BOB-G1Explore Gate not yet closedMedium

The guide prescribes producing EXPLORE-GATE.md as the Phase 1 exit artefact (architecture map, dependency graph, top-20 Plan tasks). This file does not exist in the repository. Without it, PLN-01 through PLN-06 artefacts lack a grounded baseline, and ADR decisions may be made on incomplete dependency knowledge.

BOB-G2306 uncommitted changes on mainCritical

The git status shows 306 modified files with no staging discipline. The Bob guide mandates atomic commits, evidence-based completion, and independent verification. Operating with a 306-file dirty working tree means no step can be independently verified, no rollback boundary exists, and the production readiness scorecard cannot be completed. A git hygiene task must be completed before any new implementation work.

BOB-G3Independent Verifier mode not activatedMedium

The guide specifies an i3-independent-verifier Bob mode for VER-01 through VER-08 verification phases. This mode is not yet defined in .bob/. The verify phase red-teams (tenancy isolation, approval-gate bypass) cannot be run without it.

3.2 Security Findings

SEC-01Prompt Injection Firewall — Consistent but Needs Parity CheckMedium

The 12-pattern Lobster Trap firewall is implemented in both lobster-trap.ts (TypeScript) and inline Python across admissions_agent.py, campaign_agent.py, and pmaas. The MCP server's test_prompt_injection tool validates this. A formal parity check via the sync-lobster-trap skill has not been evidenced. Run this skill to confirm no regex drift exists between TS and Python runtimes before next production deployment.

SEC-02TLS Certificate Files Committed to RepositoryCritical

The git status snapshot shows ca.crt, tls.crt, and tls.key as untracked files in the workspace root. TLS private keys must never reside in the application repository. These must be removed, rotated, and stored exclusively in OpenBao. Verify .gitignore patterns cover *.key and *.crt.

SEC-03EvalOS DB Pool — Missing Global Reuse Guard vs. EngageLow

evalos/web/src/lib/db.ts has a global reuse pattern for hot reload, but engage/web/src/lib/db.ts does not. While this is a dev-convenience concern rather than a production issue, inconsistency increases cognitive load. Standardise the pattern across all Next.js services.

SEC-04n8n Webhook in EvalOS Submit — No HMAC ValidationMedium

The EvalOS exam submit route fires an n8n webhook for exam pass/fail notifications. Unlike the engage webhooks (which should use X-Hub-Signature-256 HMAC timing-safe validation per the platform standard), the n8n call in the submit route does not show outbound HMAC signing. This means a misconfigured n8n endpoint could receive unauthenticated exam result data.

4. Architecture Findings

4.1 Onboarding Agent

ARC-01Planner hardcodes IBM Cloud credits expiryMedium

The file onboarding-agent/src/orchestrator/planner.ts hardcodes IBM Cloud credits: $14,047.27 expiring October 2026 in the static platform architecture context. This is a time-sensitive financial constant embedded in code. It should be externalised to a configuration value or removed before credits expire, as an outdated value post-October 2026 will produce incorrect agent guidance.

ARC-02Base-scan subagent uses localhost LiteLLM URLMedium

base-scan.ts points its OpenAI-compatible client to http://localhost:4000/v1. This works only in local development and will silently fail in cluster where the correct address is http://litellm-proxy.i3-model-gateway.svc.cluster.local:4000/v1. The URL should be driven by the LITELLM_URL environment variable consistently across all agents.

4.2 EvalOS Platform

ARC-03Grading service called synchronously over HTTP in submit routeMedium

The exam submission endpoint calls http://grading-service.i3-evalos.svc.cluster.local:8000/grade as a blocking synchronous HTTP call within the submit request lifecycle. Under high concurrency (e.g., exam session end), this creates a cascading latency dependency. Phase 3 (P3-T2) specifies async queue pattern for AI inference. This grading call should be similarly queued — especially given the AI-based assessment model in the generate-questions route.

ARC-04AI question generation exposes draft-state riskObservation

The admin generate-questions route correctly saves questions as is_active: false (draft, pending human review) — this is the right pattern. However, there is no workflow enforcement ensuring draft questions are reviewed before going live. A lightweight review-queue UI or approval record in the decision log would close this governance gap.

4.3 Model Gateway

ARC-05No per-tenant LiteLLM budget enforcement visibleHigh

The litellm-config-oss.yaml configures model routing, fallback chains, and semantic caching but does not show per-project or per-tenant API key budget limits. The i3 platform documentation cites "per-key budget guardrails" as a current innovation (Workstream B2), but this is not reflected in the deployed ConfigMap. Without metering enforcement, a single runaway tenant or agent can exhaust the shared Ollama pool, affecting all other tenants.

5.2 Commercial Integrity Risks (Require CEO Decision)

COM-01Data Residency Claim vs. Infrastructure RealityCritical

Multiple blueprints reference "Kenya Region" data residency. Current infrastructure is IBM ROKS Frankfurt (eu-de). The Nairobi sovereign deployment (Workstream B3, 4–6 weeks) has not been initiated. Until B3 is deployed and data-residency controls are verified, no sales or marketing collateral should reference Kenya Region residency. The Capability Claim Matrix in the Bob guide provides the correct gate for making this claim.

COM-022,500 Concurrent Students ClaimCritical

The SmartLabs blueprint identifies that 2,500 concurrent sessions requires approximately 65 worker nodes. At the current USD 3,000/month budget, the realistic concurrent-session ceiling is 70–145 students. This claim must be corrected in all customer-facing materials immediately. The budget-to-capacity mapping should be published internally so sales, pre-sales, and marketing are aligned.

COM-03GPU Acceleration Marketed Ahead of BuildHigh

GPU inference (NVIDIA L4/A10) is referenced as a platform capability in materials. All current inference runs on CPU-only Ollama workers. GPU capability should only be claimed after Workstream B1 (2–4 weeks) delivers and passes the Capability Claim Matrix gate.

COM-04Five Fragmented Revenue Models for Same ProductHigh

The AI Lab SmartLabs guide identifies five separate revenue model figures for the same product (USD 530k vs KES 154.95M vs KES 4.2B). These must be reconciled into a single authoritative pricing model before the next customer proposal. Misaligned revenue models expose the company to contractual and reputational risk.

9. What the Platform Does Well

As a Principal Architect, it is equally important to recognise what is working well and should be preserved:

  • Agent governance framework: The HC-1 through HC-8 constraint set, enforced at the Bob workspace level, is more rigorous than most enterprise AI platforms of this scale. The autonomy ceiling at L0/L1 is correctly designed.
  • Lobster Trap firewall: A 12-pattern, dual-runtime (Python + TypeScript) prompt injection firewall is a strong security posture. The MCP server validation tool closes the loop.
  • Event-driven architecture: Kafka KRaft with Pydantic-validated CloudEvent envelopes across four consumer types is well-implemented. The DLQ pattern in the Engage consumer is particularly good.
  • Database connection discipline: All services use asyncpg pools (Python) and SSL-pinned connection pools (TypeScript). The pool architecture is consistent and correct.
  • Semantic caching: LiteLLM Redis semantic cache with 0.95 similarity threshold and 1-hour TTL reduces repeat inference cost significantly.
  • KEDA autoscaling: Autoscaling across five+ services with appropriate triggers (HTTP concurrency, Kafka lag, CPU) shows production-grade operational thinking.
  • Bob engineering contract: The IBM Bob implementation guide is best-in-class for AI-assisted software engineering governance. The Capability Claim Matrix, risk-tier model, and 4-phase cycle are enterprise-grade artefacts.
  • Consent-gate pattern: The default-deny consent check in campaign_agent.py with DPA 2019 §25 compliance is a strong data-ethics implementation.

10. Conclusion

The i3 Agentic AI Platform has a strong architectural foundation. The engineering principles, agent governance model, and IBM Bob workspace configuration represent a mature approach to controlled AI-assisted platform engineering. The 3-phase modernisation roadmap is well-sequenced and the hard constraints provide a reliable safety net.

The principal risks are not architectural — they are operational hygiene (the 306-file uncommitted state, TLS keys in the workspace), commercial alignment (capability claims exceeding infrastructure reality), and two critical statutory deadline items (Hyperledger Fabric for IEBC, OTT storage migration). These are all fixable with disciplined execution of the existing roadmap.

The platform is not yet production-ready for multi-tenant GA or external customer commitments on residency and GPU capability. It is, however, well-positioned to reach that state within the Phase 1–2 timeline if the 12 recommendations above are executed in priority order.
