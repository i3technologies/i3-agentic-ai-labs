i3 Codebase Onboarding Agent

Project 1 — IBM TechXchange Hackathon 2026 · i3 Agentic AI Labs · ROKS 4.15, Frankfurt (eu-de)

A production-grade AI service that reads a real codebase, fires three subagents in parallel, verifies every referenced file path against the live repository, automatically flags stale documentation, and returns a structured 5-day role-specific ramp-up plan with Markdown, Gantt chart, and one-click CRM sync.

1. Architecture & Pipeline

Every request to POST /api/onboarding/plan passes through a strict 6-stage pipeline:

POST /api/onboarding/plan  { "role": "platform_engineer" }
         │
[1] Lobster Trap Firewall    ← 12 regex patterns block prompt injection on all user text
         │
[2] Keycloak JWT Auth        ← RS256 validation · sso.i3technologies.co.ke/realms/i3
         │
[3] Skills Assessor          ← maps role → 3 subagents (Promise.all — parallel)
    ├── infra-scan    ──────────────────────────────────────────────────┐
    ├── ailab-scan    ──────────────────────────────────────────────────┤
    └── backend-scan  ──────────────────────────────────────────────────┘
         │  each: ChromaDB RAG (topK=10) → mistral-nemo (Tier 2) → findings[]
         │
[4] Verify Pass              ← existsSync() on every filePath in findings
    └── RHOAI check: live K8s API call to /api/v1/namespaces/i3-ai-lab
         │  → verified: false + "Needs verification: ..." prefix on failure
         │
[5] Plan Synthesis           ← granite-heavy (Tier 1) · confidence gate 0.65
         │  → buildFallbackTasks() if LLM unreachable
         │
[6] Response                 ← RampUpPlan JSON + planId stored in memory
         │
    GET /plan/:id/markdown   ← Markdown with priority badges + stale-doc warnings
    GET /plan/:id/gantt      ← Mermaid Gantt chart (5 day sections)
    POST /sync/prepare       ← 🟡 stage-1 CRM sync (returns pendingId)
    POST /sync/confirm/:id   ← 🟡 stage-2 CRM sync → Directus onboarding_tasks

4. Security Design

4.1 Lobster Trap — Prompt Injection Firewall

Defined in src/security/lobster-trap.ts. Applied to every user-supplied text field (role, context, query, note) before any LLM call. Returns the matched pattern source string or null.

#PatternCatches
1ignore\s+(all\s+)?previous\s+instructions?Classic prompt injection
2you\s+are\s+now\s+(?!an?\s+(onboarding|platform|i3))Persona hijack
3act\s+as\s+(?!an?\s+(onboarding|platform|i3))Role override
4system\s*(prompt|message|instruction)System prompt exfiltration
5jailbreakJailbreak attempts
6DAN\s+modeDAN variant
7<\s*(script|img|iframe|svg)HTML / XSS injection
8(drop|delete|truncate)\s+tableSQL DDL attack
9SELECT\s+.+FROM\s+SQL data exfiltration
10prompt\s+injectionSelf-referential injection
11disregard\s+(all\s+)?previousOverride variant
12\bexfiltrate\bData exfil intent keyword

4.2 Keycloak JWT Authentication

Defined in src/security/keycloak-auth.ts. Uses jwks-rsa to fetch the public key from the Keycloak JWKS endpoint and validates RS256 tokens.

  • JWKS URI: https://sso.i3technologies.co.ke/realms/i3/protocol/openid-connect/certs
  • Issuer: https://sso.i3technologies.co.ke/realms/i3
  • Algorithm: RS256
  • Cache: 10 minutes (cacheMaxAge: 600_000)
  • On success: attaches req.user = { sub, email, preferred_username, roles[] }
  • DEV_BYPASS_AUTH=true: skips validation, injects local-dev-user with i3-admin role. Never enable in production.

4.3 RBAC — requireRole()

requireRole(...allowed) factory — place after requireAuth. Checks req.user.roles contains at least one of the allowed roles. The /api/onboarding/ingest endpoint requires role i3-admin.

4.4 Human Approval Gates

GateColourRoutesBehaviour
Automatic🟢Plan generation, retrieval, render, statusNo human step — fires immediately on valid request
One-click🟡CRM task sync (/sync/prepare → /sync/confirm/:id)Stage 1 returns pendingId (5-min TTL). Stage 2 executes Directus POST after explicit confirm. User/pendingId must match.
Never auto🔴EvalOS tables, Keycloak realm/usersBlocked in architecture. No routes exist for these writes.

4.5 Secrets

All secrets injected at runtime from OpenBao KV v2 at path i3/onboarding-agent/ via vault-agent sidecar (see onboarding-agent/openshift/deploy.yaml ServiceAccount annotation). Never in code, never in git. Keys: LITELLM_KEY, CHROMA_TOKEN, DIRECTUS_TOKEN, EVALOS_API_KEY, GITHUB_TOKEN.

5. Ingestion Layer

Transforms raw sources into RawArtifact[] objects ready for ChromaDB indexing. All connectors use makeArtifact() from src/ingestion/types.ts to ensure both field alias pairs (source/sourceType, path/filePath) are always in sync.

5.1 RawArtifact Interface

interface RawArtifact {
  source:     ArtifactSourceType;  // "platform-doc" | "platform-code" | "curriculum"
  sourceType: ArtifactSourceType;  // alias → ChromaDB source_type metadata field
  path:       string;              // relative file path (used by verify.ts)
  filePath:   string;              // alias → chunker and retriever
  content:    string;
  updatedAt:  string;              // ISO timestamp
  title?:     string;              // used in chunk metadata and Markdown render
  metadata?:  Record<string, string>;
}

6.3 Retriever (retriever.ts)

retrieve(query, {
  roleTag:     "platform_engineer",  // metadata $contains filter
  topK:        10,                   // default 8; assessor uses 10
  minScore:    0.30,                 // cosine similarity threshold (1 - distance)
  sourceTypes: ["platform-doc"]      // optional $eq / $in filter
}): Promise<RetrievedChunk[]>

retrieveAsContext(query, opts) — formats retrieved chunks as a numbered markdown context string for LLM prompts. retrieveBatch(queries, opts) — parallel multi-query variant.

6.4 Index Pipeline (index.ts)

indexArtifacts(artifacts, {verbose}) — batches chunks in groups of 200 and calls collection.upsert(). Idempotent on chunk ID (deterministic hash of filePath::chunkIndex). Returns IndexResult: {totalArtifacts, totalChunks, upsertedChunks, skippedChunks, durationMs}.

7. Orchestrator & Subagents

7.1 Skills Assessor (skills-assessor.ts)

Maps an OnboardingRole to 3 scan plans, fires each in parallel with Promise.all(). Each plan specifies: subagent class, RAG query string, roleTag filter, and focus areas list. Returns AssessmentResult { role, scanResults[], totalFindings, durationMs }.

7.2 Base Scan (subagents/base-scan.ts)

Abstract class all scanners extend. Uses mistral-nemo (Tier 2), temperature 0.2, max_tokens 2000, 2 retries. Parses LLM JSON response with Zod ScanResponseSchema — invalid JSON falls back to empty findings array without crashing.

abstract class BaseScan {
  abstract subagentName: string;
  abstract systemPrompt:  string;
  async run(input: SubagentInput): Promise<SubagentScanResult>
}

7.4 Verification Pass (verify.ts)

Runs existsSync(join(PLATFORM_REPO, filePath)) on every file path in every finding. Additionally checks whether the i3-ai-lab Kubernetes namespace is live via a real HTTP call to the cluster API.

  • Missing path → verified: false, title prefixed: "Needs verification: [title] (referenced path not found — likely stale doc)"
  • RHOAI namespace absent → same flag. platform/docs/platform-documentation.md explicitly states: "RHOAI (Month 3)". This is the key hackathon demo proof-point.
  • RHOAI check result memoized across all findings in a batch (one K8s API call per plan).
  • If KUBE_API_URL / KUBE_SA_TOKEN not set → assumes RHOAI absent (conservative default).

7.5 Planner (planner.ts)

  • Model: granite-heavy (Tier 1), temperature 0.15, max_tokens 4000
  • Confidence gate: tasks with confidence < 0.65 are filtered out
  • Output validated against RampUpPlanSchema (Zod) — malformed tasks dropped with warning
  • buildFallbackTasks() — deterministic fallback if LLM unavailable. Sorts findings by priority + day, caps at 15 tasks. Unverified tasks get confidence 0.40 (below gate, filtered unless verified).
  • Tasks sorted by day then priority (high→medium→low) before returning

8.2 Graph (graph.ts)

renderGantt(plan) — Mermaid gantt block. Priority → modifier: high=crit, medium=active, low=none. Stale-doc tasks get ⚠ prefix. Tasks truncated to 45 chars.

renderServiceGraph() — static Mermaid graph TD showing all i3 platform service dependencies: Keycloak → Admissions Agent / Onboarding Agent / EvalOS → ChromaDB → LiteLLM → Ollama/watsonx.ai → MCP → Directus/n8n → PostgreSQL → OpenBao → ArgoCD/Tekton.

8.3 Task Sync (taskSync.ts)

Implements the 2-stage confirmation gate for Directus CRM sync.

// Stage 1 — call after plan generation
prepareSyncTasks(plan, userId): SyncPreviewResult
  → { pendingId, taskCount, expiresAt (5 min), previewTasks[0..4] }

// Stage 2 — call after user clicks Confirm
confirmSyncTasks(pendingId, userId): Promise<SyncConfirmResult>
  → POSTs each task to Directus /items/onboarding_tasks
  → { success, syncedCount, skippedCount, directusIds[] }

cancelSyncTasks(pendingId): void   // user clicked Dismiss
pendingSyncCount(): number          // active pending syncs (for /status)
The pending store is an in-memory Map<string, PendingSync> with 5-minute TTL. Replace with Redis for multi-replica production deployment.
