1. Platform Architecture Overview

The i3 Agentic AI Platform is a unified, multi-tenant agentic AI system built on Red Hat OpenShift (ROKS, Frankfurt region). It operates on a one-core, many-products architecture: shared identity, model gateway, event backbone, and governance layer — with individual product applications (EvalOS, AfroERP, Engage, PMaaS, Admissions, AI Lab, Voice, Onboarding) mounted on top.

API Key Management

  1. Master key — stored in OpenBao, never used interactively. Break-glass only.
  2. Per-service virtual keys — issued via Agent Registry, scoped per tenant + model tier.
  3. To issue a new service key: add entry to Agent Registry → LiteLLM generates scoped key → key injected via OpenBao into service Secret.
  4. To revoke a key: remove from Agent Registry → key deactivated within 60 seconds.
Gap B2: A shared master key was previously in circulation. Verify it has been rotated out and all services use per-service virtual keys before production go-live.

KEDA Auto-scaling (vLLM)

KEDA ScaledObjects monitor Kafka consumer group lag and GPU memory metrics to scale vLLM worker pods. Minimum replicas: 1 (CPU), 0 (GPU — future). Maximum replicas: configurable per tenant quota in platform/model-gateway/keda/keda-scaled-objects.yaml.

5. Secrets Management (OpenBao)

Mount Layout (KV v2)

i3/
├── keycloak/admin          # Keycloak admin credentials
├── litellm/master-key      # LiteLLM master key (break-glass)
├── litellm/service-keys/   # Per-service virtual keys
├── db/postgres/            # PostgreSQL service passwords
├── kafka/credentials/      # Kafka SASL credentials
├── hmac/member-secret      # MEMBER_HMAC_SECRET (HC-6 — NID/phone anonymisation)
├── mpesa/daraja/           # M-Pesa consumer key, secret, passkey
├── kra/etims/              # KRA eTIMS PIN + API credentials
└── brevo/smtp-key          # Brevo SMTP/API key
HC-6: i3/hmac/member-secret is the MEMBER_HMAC_SECRET used for HMAC-SHA256 hashing of Kenyan National IDs and phone numbers. This key must NEVER be exposed in logs, environment variables, or code. Access via OpenBao inject sidecar only.

Secret Rotation Procedure

  1. Use the rotate-secrets Bob skill for step-by-step rotation of any i3/ mount secret.
  2. For HMAC key rotation: all previously hashed identifiers must be re-hashed. Coordinate with Data team before rotation.
  3. For DB passwords: update OpenBao KV → rolling restart of affected pods. Verify pool reconnection.
  4. For LiteLLM master key: disable old key in LiteLLM admin → update OpenBao → redeploy model-gateway pod.

OpenBao Inject Sidecar Pattern

annotations:
  vault.hashicorp.com/agent-inject: "true"
  vault.hashicorp.com/role: "i3-service-role"
  vault.hashicorp.com/agent-inject-secret-db-password: "i3/db/postgres/service-name"

Dead-Letter Queue (DLQ)

Every consumer group has a paired DLQ topic: <topic>.dlq. Unprocessable or schema-invalid events are forwarded here with a reason header. Admins must review DLQ contents daily via the Monitoring dashboard.

Row-Level Security (RLS) Pattern

-- All application queries must set the session variable:
SET LOCAL app.tenant_id = '<tenant-uuid>';

-- Policy enforced on every table:
CREATE POLICY tenant_isolation ON <table>
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
HC-4 Enforcement: Any table missing RLS or allowing queries without SET LOCAL app.tenant_id is a release blocker. Run check_rls_policy MCP tool on every DDL before deploy.

Connection Pooling (asyncpg)

  • Python services: use asyncpg.create_pool() inside FastAPI lifespan. Never asyncpg.connect() inside a request handler.
  • TypeScript services: pg pool with rejectUnauthorized: true and Crunchy Postgres CA cert mounted.
  • Max pool size: 10 per pod (tune per workload). Monitor with Prometheus pg pool metrics.

13. Tenant Provisioning

New Tenant Onboarding Steps

  1. Assign UUID — generate a new tenant_id UUID (v4). Record in platform registry.
  2. Keycloak — create realm group, assign tenant_id attribute, create initial admin user.
  3. PostgreSQL — create database schema; verify RLS policies apply tenant_id correctly.
  4. LiteLLM — issue per-tenant virtual key via Agent Registry with appropriate model tier and budget limit.
  5. Namespace — apply i3-tenant Helm template: helm upgrade --install tenant-<id> ./helm/i3-tenant --set tenantId=<uuid>
  6. Kafka — verify CloudEvent consumer validates tenantid field on all subscribed topics.
  7. OpenBao — provision tenant-scoped secrets path and policy.
  8. ChromaDB — create tenant-prefixed collection(s) if using RAG.
  9. Verify — run end-to-end smoke test: auth → LLM call → DB write → Kafka event, all with new tenant_id.
Tenant tiers: sandbox (shared resources, limited quota), standard (isolated namespace, standard quota), dedicated (dedicated node pool + private model tier). Configured via i3-tenant Helm chart values.

14. Operational Runbooks

Runbook: Kafka Consumer Lag Spike

  1. Check KEDA ScaledObject status: kubectl get scaledobject -n i3-engage
  2. Check consumer pod count: kubectl get pods -n i3-engage -l app=kafka-consumer
  3. If KEDA not scaling: verify Kafka metrics exporter is reachable by KEDA controller.
  4. If DLQ filling: inspect DLQ messages for schema errors; replay after fix.
  5. Manually scale if urgent: kubectl scale deployment/kafka-consumer --replicas=5 -n i3-engage

Runbook: LiteLLM Model Fallback Triggered

  1. Check Prometheus: litellm_fallback_total counter rising.
  2. Check Langfuse: which model triggered fallback and why (timeout / error).
  3. Inspect Ollama pod health: kubectl logs -n i3-model-gateway deployment/ollama
  4. If OOM: increase Ollama pod memory limit in vllm-deploy.yaml.
  5. If model not loaded: exec into pod and run ollama pull <model-name>.

Runbook: Auth Token Validation Failures (JWT 401)

  1. Verify Keycloak is healthy: kubectl get pods -n i3-platform -l app=keycloak
  2. Check JWKS endpoint: curl https://keycloak.i3technologies.co.ke/realms/i3/protocol/openid-connect/certs
  3. Verify service is fetching latest JWKS (token cache TTL).
  4. If realm key rotated: restart affected service pods to refresh JWKS cache.
  5. Check that tenant_id claim is present in token: decode JWT payload and inspect.

Runbook: Database Connection Pool Exhaustion

  1. Check Prometheus pg_pool_connections_active metric — identify saturated service.
  2. Check for connection leaks: look for long-running transactions in pg_stat_activity.
  3. Kill blocking connections: SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state='idle' AND query_start < NOW() - INTERVAL '10 minutes';
  4. Restart affected service pod to force pool reconnect.
  5. Review asyncpg pool configuration — ensure max_size is appropriate for replica count.

Runbook: Secret Rotation Emergency (Suspected Leak)

  1. Immediately revoke suspected secret in OpenBao: vault kv metadata delete i3/<path>
  2. Activate rotate-secrets Bob skill for step-by-step rotation.
  3. Rotate affected service keys in LiteLLM Agent Registry.
  4. Audit platform.audit-events Kafka topic for unauthorized access patterns.
  5. Submit incident report to security lead within 2 hours.
