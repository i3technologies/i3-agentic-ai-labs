4. PGBouncer Connection Pooler

Configuration

ParameterValue
Servicei3-postgres-pgbouncer.i3-data.svc.cluster.local:5432
Pool modeTransaction — a server connection is held only for the duration of a single transaction
Managed byCrunchy PGO (config lives in the PostgresCluster CR)

Critical: asyncpg / Python Applications

Prepared statements are NOT supported in PGBouncer transaction mode.

Applications using asyncpg (FastAPI, SQLAlchemy async, etc.) MUST disable prepared statement caching. Failure to do this causes cryptic errors like prepared statement "..." does not exist.

Add statement_cache_size=0 to the asyncpg connection options: 
# SQLAlchemy async engine (recommended pattern)
from sqlalchemy.ext.asyncio import create_async_engine

engine = create_async_engine(
    "postgresql+asyncpg://USER:PASS@i3-postgres-pgbouncer.i3-data.svc:5432/DBNAME",
    connect_args={"statement_cache_size": 0},
)

# Raw asyncpg connection pool
import asyncpg

pool = await asyncpg.create_pool(
    dsn="postgresql://USER:PASS@i3-postgres-pgbouncer.i3-data.svc:5432/DBNAME",
    statement_cache_size=0,
)
Do NOT append ?pgbouncer=true to connection strings. This parameter is a PgBouncer-specific hint for some ORMs but is not recognised by asyncpg and will cause connection errors. Use statement_cache_size=0 in connect_args instead.

Psycopg2 / psycopg3 (Synchronous Python)

# psycopg2 — no prepared statements by default, PGBouncer-safe as-is
import psycopg2
conn = psycopg2.connect("postgresql://USER:PASS@i3-postgres-pgbouncer.i3-data.svc:5432/DBNAME")

# psycopg3 (psycopg) — disable server-side binding
import psycopg
conn = psycopg.connect(
    "postgresql://USER:PASS@i3-postgres-pgbouncer.i3-data.svc:5432/DBNAME",
    prepare_threshold=None,   # disables prepared statements
)

Node.js / TypeScript (pg / Prisma)

// node-postgres (pg) — no prepared statements by default, safe as-is
// Prisma — add ?pgbouncer=true&connection_limit=1 to DATABASE_URL only for Prisma
DATABASE_URL="postgresql://USER:PASS@i3-postgres-pgbouncer.i3-data.svc:5432/DBNAME?pgbouncer=true&connection_limit=1"
Note: The ?pgbouncer=true query parameter is Prisma-specific only. It tells Prisma to skip its own prepared-statement logic and is safe to use. Do not add it to non-Prisma connection strings.

5. pgBackRest Backups

Backup Storage

pgBackRest stores backups in a PVC within i3-data. Backup repository details are managed by PGO in the PostgresCluster custom resource.

Known Issue: Port 8432 Timeout

Known issue: pgBackRest backup jobs may fail with a connection timeout on port 8432 error. This is a known PGO networking issue.
Status: NetworkPolicy (NP) fix has been applied. Monitor backup job logs after any cluster upgrade or pod restart. 
# Check status of recent backup jobs
kubectl -n i3-data get pods --selector=postgres-operator.crunchydata.com/pgbackrest

# View logs from the most recent backup job
kubectl -n i3-data logs -l postgres-operator.crunchydata.com/pgbackrest --tail=100

Running a Manual Full Backup

# Trigger a manual full backup via the PostgresCluster annotation
kubectl -n i3-data annotate postgrescluster i3-postgres \
  postgres-operator.crunchydata.com/pgbackrest-backup="$(date +%s)" \
  --overwrite

# Watch the backup pod come up and complete
kubectl -n i3-data get pods -w --selector=postgres-operator.crunchydata.com/pgbackrest

Verifying Backup Integrity

# Exec into the pgbackrest pod and run info
kubectl -n i3-data exec -it \
  $(kubectl -n i3-data get pods -l postgres-operator.crunchydata.com/pgbackrest -o name | head -1) \
  -- pgbackrest info

PGPASSWORD='?Z-EfajDpq21=G/5iR21>k8f' psql -U i3admin postgres

Creating a New Database and User

-- 1. Create the user with a secure password
CREATE USER new_app WITH PASSWORD 'strong-random-password-here';

-- 2. Create the database owned by the new user
CREATE DATABASE new_app_db OWNER new_app;

-- 3. Grant all privileges (connect as superuser i3admin first)
GRANT ALL PRIVILEGES ON DATABASE new_app_db TO new_app;

-- 4. Connect to the new database and set schema ownership
\c new_app_db
GRANT ALL ON SCHEMA public TO new_app;
ALTER SCHEMA public OWNER TO new_app;
After creating the database, add it to the PostgresCluster custom resource (spec.databases) so PGO manages it. Also create the corresponding Kubernetes secret in the application namespace with the connection string.

Rotating a Database Password

-- Step 1: Change password in PostgreSQL
ALTER USER app_user WITH PASSWORD 'new-secure-password';

-- Step 2: Update the Kubernetes secret in the application namespace

-- Step 3: Restart the application deployment to pick up the new secret
kubectl -n <app-namespace> rollout restart deployment <app-deployment>

# Check actual disk usage from inside a pod (exec into postgres pod)
kubectl -n i3-data exec -it i3-postgres-<pod-suffix> -c database -- df -h /pgdata

Expanding a PVC (StorageClass must support expansion)

# Edit the PVC to increase storage
kubectl -n i3-data patch pvc <pvc-name> \
  -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'

# The PV will expand online if the CSI driver supports it
kubectl -n i3-data get pvc <pvc-name> -w   # watch for resize to complete
PVC expansion requires the StorageClass to have allowVolumeExpansion: true. Check with:
kubectl get storageclass <class-name> -o yaml | grep allowVolumeExpansion

Database Disk Usage (Top tables)

-- Connect as i3admin and run per-database:
SELECT
  schemaname,
  tablename,
  pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size
FROM pg_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
LIMIT 20;

10. Troubleshooting

Connection Refused to PostgreSQL

Symptom: Application logs show connection refused or could not connect to server.
  1. Verify you are using the PGBouncer service, not the primary directly: i3-postgres-pgbouncer.i3-data.svc:5432
  2. Check PGBouncer pods are running:
    kubectl -n i3-data get pods -l postgres-operator.crunchydata.com/role=pgbouncer
  3. Check PostgreSQL cluster health:
    kubectl -n i3-data get postgrescluster i3-postgres
  4. Check pod events for crash loops or image pull errors:
    kubectl -n i3-data describe pod <pod-name>
  5. Check if a failover is in progress (the primary may be re-electing):
    kubectl -n i3-data get pods -l postgres-operator.crunchydata.com/instance

Too Many Connections

Symptom: FATAL: remaining connection slots are reserved for non-replication superuser connections or PGBouncer no more connections allowed.
  1. Check current connection count:
    SELECT count(*) FROM pg_stat_activity;
  2. Identify which databases / applications are holding excess connections:
    SELECT datname, usename, count(*) FROM pg_stat_activity GROUP BY datname, usename ORDER BY 3 DESC;
  3. Terminate idle connections that have been open too long:
    SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle'
  AND query_start < now() - interval '10 minutes'
  AND usename != 'i3admin';
  4. Check if an application is not using PGBouncer (connecting directly to the primary). All apps must use the PGBouncer service.
  5. If persistent, review the max_client_conn and pool_size settings in the PGBouncer configuration within the PostgresCluster CR.

PVC Full / Disk Pressure

Symptom: PostgreSQL pods in OOMKilled or pods crash with No space left on device. Database writes fail.
  1. Confirm disk usage:
    kubectl -n i3-data exec -it i3-postgres-<pod> -c database -- df -h /pgdata
  2. Identify large tables or databases (see Section 9 SQL queries above).
  3. Check if old WAL files are not being cleaned up — trigger a manual backup and confirm pgBackRest purges old WAL:
    kubectl -n i3-data annotate postgrescluster i3-postgres postgres-operator.crunchydata.com/pgbackrest-backup="$(date +%s)" --overwrite
  4. Expand the affected PVC (see Section 9 — PVC expansion).
  5. If the backup PVC is full, check for stale backup sets and increase retention only as a temporary measure while adding storage.

Prepared Statement Errors (asyncpg / PGBouncer)

Symptom: prepared statement "..." already exists or prepared statement "..." does not exist in application logs.

This means the application is using asyncpg without disabling prepared statement caching. Fix: add statement_cache_size=0 to the asyncpg connection arguments. See Section 4 for code examples.

SeaweedFS S3 Upload Failures

Symptom: AccessDenied or SignatureDoesNotMatch when uploading to SeaweedFS.
  1. Verify the HMAC credentials are correct — retrieve fresh values from the seaweedfs-hmac secret (see Section 6).
  2. Ensure the S3 endpoint does NOT use HTTPS — SeaweedFS in this cluster uses plain HTTP on port 8333:
    endpoint_url="http://seaweedfs-s3.i3-ott.svc.cluster.local:8333"
  3. Check SeaweedFS S3 pod logs:
    kubectl -n i3-ott logs -l app.kubernetes.io/component=s3 --tail=100
  4. Confirm the target bucket exists. SeaweedFS does not auto-create buckets:
    aws s3 ls --endpoint-url http://seaweedfs-s3.i3-ott.svc.cluster.local:8333

ChromaDB Authentication Failures

Symptom: 401 Unauthorized from ChromaDB API.

Ensure the Bearer token is being sent correctly. The token value is:

Authorization: Bearer fb4a0f0b619b6517d1b1082f5254b3c52c909221ab757f51bbc1c6a154a2c98c

Check that the ChromaDB pods are running and healthy:

kubectl -n i3-ai-lab get pods -l app=chromadb
kubectl -n i3-ai-lab logs -l app=chromadb --tail=50
