1. Architecture Overview

The i3 Agentic Runtime (i3-AR) is the central MCP (Model Context Protocol) Gateway for the i3 platform. It is the single authoritative broker through which all AI agents invoke platform capabilities — database introspection, sandboxed code execution, semantic search, and secrets retrieval — without ever having direct access to raw infrastructure.

What is an MCP Gateway?

Model Context Protocol defines a standardised JSON-RPC-like interface for AI agents to discover and call tools. Rather than each agent embedding SDK calls to databases or vaults directly, agents send structured tools/call requests to i3-AR. The gateway validates the caller's identity, checks the tier policy, executes the tool in a controlled context, writes an audit record, and returns the result. This architecture means:

  • No agent ever holds raw database credentials.
  • All tool invocations are logged, and sensitive ones require human approval.
  • Input/output is filtered by Guardian middleware before agents see results.
  • Tools can be added or removed centrally without redeploying agent models.

How Agents Connect

Agent clients (LLM orchestrators, the i3-code CLI, workflow engines) connect via HTTP/HTTPS to https://ar.i3technologies.co.ke. Every request must carry a Bearer token issued by Keycloak. The gateway validates the token, extracts the agent's identity and roles, and routes to the appropriate tool handler.

Tool Execution Flow

1
Agent sends POST /tools/call with JWT and tool name + arguments.
2
Keycloak middleware validates token; rejects with 401 if invalid or expired.
3
Guardian middleware scans input for policy violations (PII, prompt injection, disallowed content).
4
Tier policy engine checks the tool's tier. Tier 1/2 proceeds immediately; Tier 3/4 creates an ar_approvals record and returns a 202 Accepted with an approval ID.
5
Tool handler executes; result is written to ar_executions.
6
Guardian middleware scans output before it is returned to the agent.
7
Structured JSON result is returned to the agent.

2. Tier Model & Trust Levels

Every tool registered in ar_tools is assigned a tier (1–4). The tier determines the execution policy: automatic, audited, human-approved, or senior-approved.

Tier Label Policy Tools Response
Tier 1 Auto-Execute Execute immediately, minimal audit read_db_schema, query_curriculum_vector 200 OK — result
Tier 2 Audited Execute Execute immediately, full audit log with caller identity execute_sandboxed_code (limited permissions) 200 OK — result + execution_id
Tier 3 Human Approval Queued; IT staff must approve via approval API vault_get_secret (sensitive paths), bulk DB ops 202 Accepted — approval_id
Tier 4 Senior IT Approval Queued; Senior IT admin must approve Production DB writes, external API calls with PII 202 Accepted — approval_id
Tier 3/4 blocking: The agent call returns a 202 immediately. The actual tool result is only available after a reviewer approves it via PATCH /approvals/{id}. Agents must poll or use a callback mechanism to retrieve the final result.

Tier Override

Admins can temporarily override a tool's tier by updating the tier column in ar_tools. Always revert after the maintenance window and document the change in the audit log.

3. MCP Tool Endpoints

All tool calls go through a single dispatch endpoint. The tool name selects the handler; arguments are passed in the arguments object. All requests require a valid Bearer JWT.

POST /tools/list

Returns all registered MCP tools with their schemas. Used by agents for capability discovery.

curl -s https://ar.i3technologies.co.ke/tools/list \
  -H "Authorization: Bearer $TOKEN" | jq .

Tool 1 — read_db_schema Tier 1

Returns table and column metadata from any platform database. Agents use this to understand schema structure before formulating queries. No data rows are ever returned.

4. Approval Workflow (Tier 3/4 Human-in-the-Loop)

When a Tier 3 or Tier 4 tool is invoked, the gateway does not execute it immediately. Instead, a record is inserted into ar_approvals with status pending. A designated reviewer must inspect the request and approve or reject it.

Listing Pending Approvals

GET /approvals/pending

Returns all approval records with status pending. Reviewers should check this regularly (or configure alerting).

curl -s https://ar.i3technologies.co.ke/approvals/pending \
  -H "Authorization: Bearer $ADMIN_TOKEN" | jq .

Response (200 OK)

[
  {
    "id": "apr_5e1f22",
    "tool": "vault_get_secret",
    "arguments": { "path": "secret/data/i3-ar/smtp-password" },
    "caller": "agent:workflow-engine-03",
    "tier": 3,
    "status": "pending",
    "created_at": "2025-01-15T10:32:00Z",
    "trace_id": "trace_8a4b01"
  }
]

Approving or Rejecting an Action

PATCH /approvals/{id}

  "id": "apr_5e1f22",
  "status": "approved",
  "reviewed_at": "2025-01-15T10:45:12Z",
  "reviewer": "john.kamau",
  "execution_id": "exec_6d3a11"

SLA guidance: Tier 3 approvals should be reviewed within 30 minutes. Tier 4 approvals require a senior IT admin and should be reviewed within 2 hours. Configure PagerDuty or Slack alerts on new pending records in ar_approvals.

Approval Escalation Flow

Agent invokes Tier 3/4 tool
        │
        ▼
  Gateway inserts ar_approvals record (status=pending)
        │
        ├── Notifies reviewer via alert channel
        │
        ▼
  Reviewer calls PATCH /approvals/{id}
        │
        ├── status=approved → Tool executes → result stored in ar_executions
        │                                    → agent notified
        │
        └── status=rejected → ar_approvals.status=rejected
                             → agent receives rejection notice with reason

6. Execution Log — ar_executions Table

Every tool invocation (successful or failed) is written to ar_executions. This is the primary audit trail for all agent actions on the platform.

Schema

ColumnTypeDescription
idUUIDExecution ID (returned to caller)
tool_nameVARCHARName of the tool invoked
callerVARCHARAgent/user identity from JWT sub claim
argumentsJSONBSanitised input arguments (secrets redacted)
resultJSONBTool output (sensitive values redacted)
statusVARCHARsuccess, error, timeout, policy_violation
tierINTTier at time of execution
duration_msINTExecution duration in milliseconds
trace_idVARCHARDistributed trace ID for correlation
created_atTIMESTAMPTZWhen execution occurred

Common Audit Queries

-- All executions in the last 24 hours
SELECT tool_name, caller, status, duration_ms, created_at
FROM ar_executions
WHERE created_at > NOW() - INTERVAL '24 hours'
ORDER BY created_at DESC;

-- Policy violations
SELECT * FROM ar_executions WHERE status = 'policy_violation';

-- Executions by a specific agent
SELECT * FROM ar_executions
WHERE caller = 'agent:code-agent-01'
ORDER BY created_at DESC LIMIT 50;

-- Slowest executions (over 5 seconds)
SELECT tool_name, caller, duration_ms, created_at
FROM ar_executions
WHERE duration_ms > 5000
ORDER BY duration_ms DESC;

7. OpenBao/Vault Integration

The vault_get_secret tool communicates with OpenBao (an open-source Vault-compatible secrets manager) running in the cluster. The gateway authenticates to OpenBao using a Kubernetes service account token (Kubernetes Auth method).

How It Works

1
The agent request arrives with a path argument (e.g. secret/data/i3-ar/smtp-password).
2
Tier policy engine creates an ar_approvals record; returns 202 to the agent.
3
After approval, the gateway POSTs a GET to OpenBao's KV API using its own service token: GET {VAULT_ADDR}/v1/{path}.
4
OpenBao returns the secret. The value is passed to the agent; it is never stored in ar_executions.

Vault Configuration (in i3-ar-secrets)

kubectl get secret i3-ar-secrets -n i3-ar -o jsonpath='{.data}' | \
  jq 'to_entries[] | {key: .key, value: (.value | @base64d)}'

# Key environment variables consumed by i3-AR:
# VAULT_ADDR     — OpenBao API address (e.g. http://openbao.i3-vault:8200)
# VAULT_TOKEN    — Service token with read-only policy on secret/data/i3-ar/*
# VAULT_ROLE     — Kubernetes auth role name

Checking Vault Connectivity

# From within the pod
kubectl exec -n i3-ar -it \
  $(kubectl get pod -n i3-ar -l app=ar -o jsonpath='{.items[0].metadata.name}') \
  -- curl -s -H "X-Vault-Token: $VAULT_TOKEN" \
     $VAULT_ADDR/v1/sys/health | jq .
Path whitelist: The gateway enforces a configurable allowlist of Vault paths that agents may request. Requests to paths outside the allowlist are rejected at the tier policy stage with a 403 — no approval record is created.

8. ChromaDB Integration

The query_curriculum_vector tool queries a ChromaDB instance that holds embeddings of all i3 platform curriculum content. Embeddings are generated using a sentence-transformer model and stored with metadata (course, unit, page).

Collection Details

PropertyValue
Collection namei3_curriculum
Embedding modelsentence-transformers/all-MiniLM-L6-v2

ChromaDB endpointConfigured in CHROMADB_URL env var

How It Works

1
The agent's query string is embedded using the same model as the collection.
2
ChromaDB performs an approximate nearest-neighbour search.
3
Top-N chunks with their metadata and cosine distances are returned.

9. Adding a New MCP Tool (Developer Guide)

New tools can be added to the gateway by registering them in ar_tools and implementing a handler in the FastAPI application. Follow this procedure:

1
Define the handler — Create a Python async function in app/tools/: 
# app/tools/send_notification.py
from app.models import ToolResult

async def send_notification(recipient: str, message: str) -> ToolResult:
    """Send a notification via the platform notification service."""
    # ... implementation ...
    return ToolResult(output={"sent": True, "recipient": recipient})
2
Register in ar_tools: 
INSERT INTO ar_tools (id, name, description, input_schema, tier, handler, enabled)
VALUES (
  gen_random_uuid(),
  'send_notification',
  'Send a notification to a user via the platform notification service.',
  '{
    "type": "object",
    "properties": {
      "recipient": {"type": "string"},
      "message":   {"type": "string"}
    },
    "required": ["recipient", "message"]
  }',
  2,
  'app.tools.send_notification.send_notification',
  true
);
3
Reload the tool registry — The gateway caches the registry at startup. Trigger a rolling restart: 
kubectl rollout restart deployment/ar -n i3-ar
4
Verify registration: 
curl -s https://ar.i3technologies.co.ke/tools/list \
  -H "Authorization: Bearer $TOKEN" | \
  jq '.tools[] | select(.name=="send_notification")'
Tier assignment guidance: Read-only, non-sensitive tools → Tier 1. Tools that mutate state or run code → Tier 2. Tools that access secrets or PII → Tier 3. Tools that write to production systems → Tier 4.

10. Keycloak Authentication for Agent Clients

All callers (agents, CLI tools, workflow engines) must obtain a JWT from Keycloak before calling i3-AR. The gateway validates every request against the Keycloak JWKS endpoint.

Client Configuration

PropertyValue
Client IDi3-ar-server
Access typeConfidential (server-to-server agents)
Secret locationi3-ar-secrets Secret · key KEYCLOAK_CLIENT_SECRET
Grant typeClient Credentials (for automated agents)
Token endpointhttps://auth.i3technologies.co.ke/realms/i3/protocol/openid-connect/token

Obtaining a Token (Client Credentials — for agents)

export TOKEN=$(curl -s -X POST \
  https://auth.i3technologies.co.ke/realms/i3/protocol/openid-connect/token \
  -d "client_id=i3-ar-server" \
  -d "client_secret=$KEYCLOAK_CLIENT_SECRET" \
  -d "grant_type=client_credentials" \
  | jq -r '.access_token')

echo $TOKEN | cut -d. -f2 | base64 -d 2>/dev/null | jq .  # inspect claims

Token Validation

The gateway uses FastAPI's dependency injection with python-jose to validate tokens. It checks:

  • Signature against Keycloak's JWKS (/realms/i3/protocol/openid-connect/certs)
  • Audience (aud must include i3-ar-server)
  • Expiry (exp claim)
  • Required roles in realm_access.roles

Required Roles

RolePermissions
ar-agentCall Tier 1 and Tier 2 tools
ar-agent-elevatedSubmit Tier 3/4 requests (still requires human approval)
ar-reviewerAccess GET /approvals/pending and PATCH /approvals/{id}
ar-adminFull access including tool registry management

11. Guardian Middleware

Every request through i3-AR passes through the Guardian middleware layer before reaching the tool handler and again before the response is returned to the agent. Guardian uses IBM Granite Guardian (a safety/policy model) to filter both inputs and outputs.

What Guardian Checks

CheckDirectionAction on Violation
Prompt injection patternsInboundReject 400 + log POLICY_VIOLATION
PII in tool argumentsInboundRedact and warn, or reject (configurable)
Disallowed content categoriesInboundReject 400
PII in tool resultsOutboundRedact before returning to agent
Sensitive data patterns (keys, passwords in stdout)OutboundRedact before returning
Hallucinated tool namesInboundReject 404

Configuration

# Guardian config is in the i3-ar ConfigMap
kubectl get configmap ar-config -n i3-ar -o yaml

# Key settings:
# GUARDIAN_ENABLED: "true"
# GUARDIAN_MODEL: "ibm/granite-guardian-3-2b"
# GUARDIAN_PII_REDACT: "true"
# GUARDIAN_INJECT_BLOCK: "true"
# GUARDIAN_ENDPOINT: "http://guardian-svc.i3-guardian:8080"

Viewing Guardian Decisions

# Guardian violations appear in ar_executions with status=policy_violation
SELECT
  id, tool_name, caller, arguments,
  result->>'guardian_reason' AS guardian_reason,
  created_at
FROM ar_executions
WHERE status = 'policy_violation'
ORDER BY created_at DESC LIMIT 20;

14. i3-Code CLI Developer Tool

The i3-code CLI is a companion terminal tool for developers that connects to the i3-AR MCP Gateway. It provides three interaction modes and authenticates via OIDC device flow — no stored passwords.

Client Configuration

PropertyValue
Keycloak Client IDi3-code-cli
Access typePublic (no client secret)
Grant typeDevice Authorization Flow (RFC 8628)
MCP Gatewayhttps://ar.i3technologies.co.ke

Authentication — OIDC Device Flow

The CLI uses the OAuth 2.0 Device Authorization Grant. No password is entered in the terminal; the developer authenticates in a browser:

# First login — opens browser for device auth
i3-code login

# Output:
# → Open https://auth.i3technologies.co.ke/activate
# → Enter code: WXYZ-1234
# → Waiting for authorization...
# ✓ Authenticated as: dev@i3technologies.co.ke
# Token stored in ~/.i3/credentials.json

CLI Modes

ModeCommandDescription
Aski3-code ask "explain the OSI model"Single-turn Q&A. Calls query_curriculum_vector for context, then LLM completion. No code execution.
Plani3-code plan "add a new API endpoint for course exports"Multi-step planning mode. Calls read_db_schema to understand data model, generates a structured implementation plan. Does not execute changes.
Agenti3-code agent "fix the failing test in billing module"Agentic mode. Can call all MCP tools, execute sandboxed code, iterate on results. Prompts for confirmation on Tier 3/4 actions.

Common CLI Workflows

# Ask a question backed by curriculum search
i3-code ask "what are the prerequisites for CCNA certification?"

# Plan a database change
i3-code plan "add an audit log table to lms_db"

# Agent mode: write and test a Python function
i3-code agent "write a function to validate Kenya phone numbers and run its tests"

# Check what tools are available
i3-code tools list

# View token info
i3-code auth whoami

# Logout (clears stored token)
i3-code logout

CLI Configuration File

# ~/.i3/config.yaml
mcp_gateway: https://ar.i3technologies.co.ke
keycloak_url: https://auth.i3technologies.co.ke
realm: i3
client_id: i3-code-cli
default_model: ibm/granite-3-8b-instruct

CLI Token Refresh

The CLI automatically refreshes the access token using the stored refresh token. If the refresh token expires (default: 30 days), the developer must re-run i3-code login.

For admins: The i3-code-cli client in Keycloak is configured with the ar-agent realm role by default. Grant ar-agent-elevated to developers who need to invoke Tier 3 tools directly from their terminals.
