1. Platform Mission & Architecture Summary

The i3 Agentic AI Platform is a multi-tenant, cloud-native AI infrastructure hosted on IBM Red Hat OpenShift Kubernetes Service (ROKS) in the Frankfurt (eu-de) region. It serves as the unified technology backbone for i3 Technologies Ltd and its ecosystem of products and clients.

The platform delivers the following capabilities from a single OpenShift cluster:

AI & LLM Services

  • LiteLLM multi-model proxy gateway
  • Ollama local LLM server (Mistral, Granite)
  • Open WebUI (Sage) — chat interface
  • JupyterHub — AI notebook environment
  • ChromaDB — vector database
  • Langfuse — LLM observability

Business Applications

  • EvalOS — AI-powered assessment platform
  • PMaaS — Project & campaign management
  • AfroERP (ERPNext) — Enterprise ERP
  • Moodle (EdBridge) — Learning management
  • Engage — WhatsApp/SMS/email hub
  • Nextcloud — Collaboration & storage

New Platform Services (2026)

  • SIT Digital Work-Centers — TVET/eCitizen
  • Talent Cloud — Candidate & job matching
  • FORD-Asili — Blockchain membership/PMaaS
  • MCP Gateway (i3-AR) — Agentic runtime
  • SmartLab — IoT/lab management API
  • Voice STT/TTS — Speech services

Platform Infrastructure

  • Keycloak / Red Hat SSO — Identity & auth
  • PostgreSQL HA — Primary database cluster
  • SeaweedFS — Distributed object storage
  • Kafka — Event streaming
  • OpenBao (Vault) — Secrets management
  • Grafana / Prometheus — Observability
  • ArgoCD — GitOps deployment
  • n8n — Workflow automation

7. Networking & Security Model

NetworkPolicy Strategy

Every namespace follows the default-deny-all + explicit allow pattern:

  • A deny-all-ingress NetworkPolicy blocks all intra-cluster traffic by default in all data namespaces.
  • Explicit allow-* policies open only the required ports between namespaces.
  • DNS egress uses both a namespace selector (openshift-dns) and an IP block (172.21.0.10/32) to ensure name resolution works.
  • Image registry egress uses both a namespace selector (openshift-image-registry) and an IP block (172.21.59.183/32).

Database Access Control (i3-data)

The i3-data namespace has two key NetworkPolicies that control which namespaces may reach PostgreSQL and PGBouncer:

8. Build & Deployment Pattern

All application builds use OpenShift's internal S2I/Docker build system. Docker Hub and registry.access.redhat.com are unreachable from build pods — all Python apps must use openshift/python:3.11-slim imagestream from the internal registry.

Standard Build & Deploy Procedure

# 1. Set KUBECONFIG
$env:KUBECONFIG = "$env:USERPROFILE\.bluemix\plugins\container-service\clusters\i3-platform-da0umukf0anep6valpig-admin\kube-config.yaml"

# 2. Create a BuildConfig (first time only)
oc new-build --name=APP_NAME --image-stream=openshift/python:3.11-slim --binary -n NAMESPACE

# 3. Start build from local source directory
oc start-build APP_NAME -n NAMESPACE --from-dir=platform/APP_DIR

# 4. Check build status
oc get builds -n NAMESPACE --no-headers | Select-Object -Last 3

# 5. Rollout the new image
oc rollout restart deployment/APP_NAME -n NAMESPACE

# 6. Wait for rollout
oc rollout status deployment/APP_NAME -n NAMESPACE --timeout=120s
Note on --follow: The oc start-build --follow flag always times out after ~5 minutes in PowerShell. Use oc get builds to check status instead. Builds typically complete in 15–22 minutes.

10. Daily Operations Runbook

Health Check — Run Daily

# Quick cluster health
$env:KUBECONFIG = "$env:USERPROFILE\.bluemix\plugins\container-service\clusters\i3-platform-da0umukf0anep6valpig-admin\kube-config.yaml"
oc get nodes --no-headers
oc get pods -A --no-headers | Where-Object { $_ -notmatch "Running|Completed" }  # Shows only unhealthy pods

Check All Endpoints (30-second sweep)

$apps = @("sso","grafana","n8n","vault","evalos","engage","moodle","afroerp","cms","jupyter","sage","nextcloud","litellm","langfuse","pmaas","argocd")
foreach ($a in $apps) {
  $code = curl.exe -sk --max-time 6 -o NUL -w "%{http_code}" "https://$a.i3technologies.co.ke"
  Write-Output "$code  $a.i3technologies.co.ke"
}

Restart a Deployment

# Graceful rolling restart
oc rollout restart deployment/DEPLOYMENT_NAME -n NAMESPACE
oc rollout status deployment/DEPLOYMENT_NAME -n NAMESPACE

View Logs

# Last 50 lines from a pod
oc logs -n NAMESPACE POD_NAME --tail=50

# Follow live logs
oc logs -n NAMESPACE POD_NAME -f

# From a deployment (picks any healthy pod)
oc logs -n NAMESPACE deployment/DEPLOYMENT_NAME --tail=50

Scale a Deployment

# Scale down (maintenance)
oc scale deployment/DEPLOYMENT_NAME --replicas=0 -n NAMESPACE

# Scale back up
oc scale deployment/DEPLOYMENT_NAME --replicas=2 -n NAMESPACE

Check PVC Usage

oc get pvc -A --no-headers | Where-Object { $_ -match "^i3" }

12. Backup Strategy

PostgreSQL — pgBackRest

The PostgreSQL HA cluster is managed by Crunchy Data Postgres Operator (PGO) with pgBackRest configured for both full and differential backups stored in SeaweedFS S3.

Backup TypeScheduleRetention
Full backupDaily at 02:00 UTC7 days
Differential backupEvery 6 hours48 hours
Known issue: pgBackRest backup jobs have been failing with HostConnectError timeout on port 8432. The NetworkPolicy fix has been applied. Run oc get pods -n i3-data | Select-String "repo1" to check for failed jobs and clean with oc delete pods -n i3-data -l pgbackrest-backup=repo1-full.
# Trigger manual full backup
oc exec -n i3-data \
  $(oc get pods -n i3-data -l postgres-operator.crunchydata.com/role=master --no-headers | head -1 | awk '{print $1}') \
  -- pgbackrest backup --stanza=db --type=full

Persistent Volume Snapshots

IBM VPC Block Storage supports volume snapshots via the IBM Cloud Console. Critical PVCs to snapshot regularly:

  • data-seaweedfs-volume-* (1.5 TiB object storage)
  • edbridge-data (Moodle files)
  • ollama-data-ollama-0 (LLM model weights — 80 GiB)
  • n8n-data-pvc (n8n workflows)

13. Disaster Recovery

RTO / RPO Targets

TierSystemsRTORPO
Tier 1 — CriticalKeycloak SSO, PostgreSQL, PGBouncer15 min1 hour
Tier 2 — ImportantEvalOS, Engage, LiteLLM, n8n, Vault1 hour4 hours
Tier 3 — StandardAll other applications4 hours24 hours

Recovery Steps

  1. Cluster unreachable: Log in to IBM Cloud console → Kubernetes → Cluster → Reboot nodes or contact IBM Support.
  2. Namespace broken: oc get events -n NAMESPACE | tail -20 to diagnose, then redeploy from GitOps/ArgoCD.
  3. Database corruption: Use pgBackRest restore: pgbackrest restore --stanza=db --delta from primary pod.
  4. Secret lost: Retrieve from OpenBao vault (requires root token) or re-generate and patch the secret + rollout restart.
  5. LB/DNS issue: All CNAME records point to 8eec2322-eu-de.lb.appdomain.cloud. Verify at cPanel (cpanel.i3technologies.co.ke:2083).
