1. Problem Statement & Business Case

New engineers routinely lose their first one to two weeks piecing together tribal knowledge scattered across READMEs, wikis, architecture docs, and old tickets — with no single, current view of how the codebase actually works. Generic onboarding docs answer questions a mentor anticipated; they cannot adapt to role, seniority, or the actual current state of the repository.

Core Problem Onboarding is slow, generic, and stale. The README often contradicts the code. Historical decisions live in closed tickets no one reads. New engineers make their first PR 8–14 days later than they could if they had a guided, repo-specific plan.
Proposed Solution An agent that ingests the repository's full documentation set, ticket history, and design docs — then uses IBM Bob 2.0 Agent Mode + parallel Subagents to generate a personalized, role-specific, verified ramp-up plan where every task references a real, current file path. Stale references are caught and flagged automatically.

4. Core Data Flow — End-to-End Pipeline
Stage 1 — Ingestion

The ingestRepo(owner, repo) function in src/ingestion/github.ts uses Octokit to fetch the full git tree, filter for README/ADR/docs paths, fetch content for each, and paginate all closed GitHub Issues. Every artifact is tagged with a source type ("readme" | "issue" | "adr" | "wiki"), a path, content, and updatedAt timestamp. Output: RawArtifact[].

Stage 2 — Chunking & Indexing

buildContextStore(artifacts) in src/context-store/index.ts splits each artifact into 500-word chunks via chunkText(), assigns IDs as ${sourcePath}-${chunkIndex}, stores chunk text + metadata in the Chroma collection "onboarding-corpus" (local SQLite). This runs once per ingest cycle. Retrieval uses retrieveRelevant(collection, query, k) with k=12 for the planner and k=10 per subagent.

Stage 3 — Orchestration (The Core Loop)

runRoleScans() in src/orchestrator/subagents.ts fires three Bob 2.0 subagents concurrently via Promise.all(): backend-scan, frontend-scan, infra-scan. Each receives its top-10 relevant chunks from Chroma. Results merge into the planner context. generatePlan(role, collection, bob) then calls Bob 2.0 Agent Mode with the combined context and the RampUpPlan output schema. After generation, every task.referencedPath is verified via repoContainsPath(). Tasks with paths not found are marked verified: false and retitled "Needs verification: [title] (referenced path not found — likely stale doc)".

Stage 4 — Rendering & Sync

markdownPlan.ts renders the verified RampUpPlan as an HTML page. graph.ts emits a mermaid DAG color-coded by git commit churn. taskSync.ts creates one GitHub Issue per task with verification status annotated in the body. server.ts exposes this through routes and serves the demo UI.

Full Pipeline Command npm run ingest -- --repo=your-org/seed-repo → prints chunk counts per source type. This is the Day 1 completion criterion.

Ingestion — github.ts Core Function
export async function ingestRepo(owner: string, repo: string): Promise<RawArtifact[]> {
  const octokit = new Octokit({ auth: process.env.GITHUB_TOKEN });
  // Pull file tree, filter README/ADR/docs paths, decode Base64 content
  const { data: tree } = await octokit.git.getTree({
    owner, repo, tree_sha: "main", recursive: "true"
  });
  // Pull all closed issues via paginate
  const issues = await octokit.paginate(octokit.issues.listForRepo, {
    owner, repo, state: "closed", per_page: 100
  });
  return artifacts; // RawArtifact[] tagged with source, path, content, updatedAt
}
Context Store — 500-word Chunking + Chroma Index
// Collection: "onboarding-corpus" | Chunk size: 500 words | ID: "${path}-${i}"
export async function buildContextStore(artifacts: RawArtifact[]) {
  const collection = await client.getOrCreateCollection({ name: "onboarding-corpus" });
  const chunks = artifacts.flatMap(a =>
    chunkText(a.content, 500).map((c, i) => ({
      id: `${a.path}-${i}`, text: c,
      metadata: { source: a.source, path: a.path, updatedAt: a.updatedAt }
    }))
  );
  await collection.add({ ids, documents, metadatas });
}
Subagents — Concurrent Execution (Promise.all)
export async function runRoleScans(collection: any, bob: BobClient) {
  const [backend, frontend, infra] = await Promise.all([
    bob.subagent("backend-scan", {
      context: await retrieveRelevant(collection, "backend architecture and entry points", 10)
    }),
    bob.subagent("frontend-scan", {
      context: await retrieveRelevant(collection, "frontend structure and build tooling", 10)
    }),
    bob.subagent("infra-scan", {
      context: await retrieveRelevant(collection, "deployment, CI/CD, and infra config", 10)
    }),
  ]);
  return { backend, frontend, infra };
}
Verification Loop — Stale Reference Detection
for (const task of plan.weekOneTasks) {
  task.verified = await repoContainsPath(task.referencedPath);
  if (!task.verified) {
    // Do NOT silently drop — this is the "agent catches its own stale claim" demo moment
    task.title = `Needs verification: ${task.title} ` +
                 `(referenced path not found — likely stale doc)`;
  }
}
Task Sync — Push to GitHub Issues
export async function syncTasksToTracker(plan: RampUpPlan, octokit, owner, repo) {
  for (const task of plan.weekOneTasks) {
    await octokit.issues.create({
      owner, repo,
      title: `[Onboarding] ${task.title}`,
      body: `Auto-generated first-week task.\n` +
            `Referenced: \`${task.referencedPath}\`\n` +
            `Verified against current repo: ${task.verified ? "yes" : "no — stale reference"}`,
      labels: ["onboarding", plan.role],
    });
  }
}
10. Human Approval Gates

All agent actions are tiered by risk level. This is a feature — not a limitation. Judges will respect explicit human-in-the-loop design.

Green — Act and report automatically: Generate and render the ramp-up plan. Post style comments to a PR. Surface verification results in the UI.
Yellow — Prepare action, hold for one-click approval: Create GitHub Issues from generated task list. Push onboarding tasks to Jira/Linear. Requires human to confirm before sync executes.
Red — Draft only, human must explicitly approve: Any modification to the target repository's code or documentation. Any write to a production system. Never demo auto-merge.
