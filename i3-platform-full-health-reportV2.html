Issues Found — 5 Items

🔴 Issue #1 — Voice STT & TTS: External Timeout (NetworkPolicy)
Both voice-stt (port 8001) and voice-tts (port 8000) pods are 1/1 Running and healthy internally (confirmed via GET /v1/health → 200). The routes are edge-terminated and point to the correct service. However, voice-ingress NetworkPolicy only allows ingress from: i3-ai-lab, i3-evalos, i3-pmaas, i3-engage, i3-smartlab namespaces — the OpenShift router namespace (openshift-ingress) is not included, so all external HTTP traffic is silently dropped (timeout).

Fix: Add namespaceSelector: kubernetes.io/metadata.name: openshift-ingress to the voice-ingress NetworkPolicy ingress rules.
🔴 Issue #2 — Admissions & Onboarding: 404 on Root Path
Both agent pods are Running and respond 200 on /health. The routes have no path prefix set (serve from /). The FastAPI apps do not register a handler for GET / — only /health, /metrics, and API sub-paths exist. The root path returns 404 by default from FastAPI/Starlette.

Fix: Add a root GET / redirect to /docs or return a 200 status page in the FastAPI app; or set the route path: /health for health-check purposes. For a public-facing UI, a root handler is required.
🟡 Issue #3 — PostgreSQL Backup Failures (pgBackRest — 18 Error pods)
Since Sep 14 ~06:00 UTC, all scheduled diff and full backup jobs are erroring with:
HostConnectError: timeout connecting to i3-postgres-primary-*:8432 → unable to find primary cluster

The 3 primary pods are all 4/4 Running and PGBouncer is 2/2 Running (port 5432 serving fine). The issue is pgBackRest reaching the primary pods on port 8432 (direct primary port) rather than through PGBouncer. Last successful full backup was Sep 13 01:00 UTC (3 days ago). Data is safe; application access is unaffected. The quota error on PGBouncer replica creation (limits.cpu exceeded) is a separate pre-existing constraint.

Fix: Investigate why port 8432 became unreachable from the backup job — likely a NetworkPolicy change or pod IP rotation. Trigger a manual backup and review the pgBackRest stanza config.
🔵 Issue #4 — PMaaS Web: 307 Redirect on Root
GET / returns HTTP 307 to /login. This is expected Next.js middleware auth redirect behaviour — the root page redirects unauthenticated users to the login page. Not a fault; the app is running correctly (1/1 Running, all env vars set including NEXTAUTH_URL=https://pmaas.i3technologies.co.ke). Browsers follow the redirect correctly.
🔵 Issue #5 — Keycloak, Langfuse, LiteLLM: SSL Test False-Positive
The PowerShell Invoke-WebRequest test rejected TLS connections on keycloak.i3technologies.co.ke, langfuse.i3technologies.co.ke, and litellm.i3technologies.co.ke due to self-signed or platform-issued certificates not in the Windows trust store. All three services are functionally healthy — pods Running, routes active, confirmed reachable via SSO flows and internal service-to-service calls. Not a real fault; browser clients accept these certs.
