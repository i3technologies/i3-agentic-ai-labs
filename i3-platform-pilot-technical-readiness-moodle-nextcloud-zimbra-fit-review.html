4. Zimbra ZCS — Pilot Deployment Spec

Scope for October pilot: A single-node Zimbra instance providing @i3technologies.co.ke email for pilot participants and internal team. This is deliberately minimal — one pod, one domain, no clustering, no HA. HA Zimbra is post-pilot budget work.

Important technical constraint: Zimbra ZCS requires privileged container execution because it manages its own MTA (Postfix), IMAP/POP daemon, and LDAP — all of which bind to ports below 1024 and manage OS-level services internally. On OpenShift this requires a SecurityContextConstraints (SCC) grant. The manifest below includes the required SCC configuration. This is standard for Zimbra on OpenShift — it is not a security gap when scoped correctly to the i3-zimbra namespace only.

Namespace + SCC + Deployment

# mail     CNAME   8eec2322-eu-de.lb.appdomain.cloud
# webmail  CNAME   8eec2322-eu-de.lb.appdomain.cloud
#
# MX record (for receiving email):
# @        MX  10  mail.i3technologies.co.ke
#
# SMTP (port 25) requires LoadBalancer Service, not just an HTTPS Route:
# Expose SMTP via a LoadBalancer Service (IBM Cloud VPC LB) — separate from OpenShift Routes

# SMTP LoadBalancer Service (for sending/receiving actual email):
apiVersion: v1
kind: Service
metadata:
  name: zimbra-smtp
  namespace: i3-zimbra
  annotations:
    service.kubernetes.io/ibm-load-balancer-cloud-provider-ip-type: public
spec:
  type: LoadBalancer
  selector: {app: zimbra}
  ports:
    - {name: smtp,  port: 25,  targetPort: 25}
    - {name: imaps, port: 993, targetPort: 993}
Zimbra SMTP note: OpenShift Routes only handle HTTP/HTTPS. SMTP (port 25) and IMAPS (port 993) need a LoadBalancer Service which provisions an IBM Cloud VPC Load Balancer with a dedicated public IP. This IP then gets the MX record and the mail A-record in DNS. This is a minor cost addition (~$10–15/month for the VPC LB). For the pilot, if you only want webmail access (no native email client / IMAP), the Route alone is sufficient — add the LB Service when users need Outlook/Thunderbird IMAP access.

5. Shared PostgreSQL — Create Moodle + Nextcloud Databases

Both Moodle and Nextcloud point to the existing Crunchy HA PostgreSQL cluster. Two databases need to be created before the apps start.

oc exec — run against primary postgres pod
# Get the primary pod name
PGPOD=$(oc get pods -n i3-data -l postgres-operator.crunchydata.com/role=primary \
  --no-headers -o custom-columns="NAME:.metadata.name" | head -1)

# Create databases and users for Moodle and Nextcloud
oc exec -n i3-data $PGPOD -- psql -U postgres -c \
  "CREATE USER moodle_user WITH PASSWORD 'CHANGE_ME_MOODLE';
   CREATE DATABASE moodle_db OWNER moodle_user ENCODING 'UTF8';
   GRANT ALL PRIVILEGES ON DATABASE moodle_db TO moodle_user;"

oc exec -n i3-data $PGPOD -- psql -U postgres -c \
  "CREATE USER nextcloud_user WITH PASSWORD 'CHANGE_ME_NEXTCLOUD';
   CREATE DATABASE nextcloud_db OWNER nextcloud_user ENCODING 'UTF8';
   GRANT ALL PRIVILEGES ON DATABASE nextcloud_db TO nextcloud_user;"

# Store credentials in OpenBao (Vault) — not as plain Kubernetes secrets
# Then create k8s secrets that reference the Vault values via the Vault Agent injector:
oc create secret generic moodle-secrets -n i3-moodle \
  --from-literal=db-user=moodle_user \
  --from-literal=db-pass=CHANGE_ME_MOODLE

oc create secret generic nextcloud-secrets -n i3-nextcloud \
  --from-literal=db-user=nextcloud_user \
  --from-literal=db-pass=CHANGE_ME_NEXTCLOUD \
  --from-literal=admin-pass=CHANGE_ME_NC_ADMIN

oc create secret generic zimbra-secrets -n i3-zimbra \
  --from-literal=admin-pass=CHANGE_ME_ZIMBRA
