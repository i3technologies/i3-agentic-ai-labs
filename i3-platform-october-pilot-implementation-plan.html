Phase A — Immediate Cluster Fixes (Do Right Now · ~2 hours)
1
Retire sk-i3-internal — Issue Per-Team LiteLLM Virtual Keys
Security isolation — required before any pilot user touches the platform · ~2–4 h
  • Create one virtual key per pilot team via LiteLLM Admin UI at https://litellm.i3technologies.co.ke
  • Set max_budget: 5.0 (USD) and rpm_limit: 20 per key — prevents any single team burning all compute
  • Remove sk-i3-internal from JupyterHub configmap env injection — update LITELLM_KEY and OPENAI_API_KEY to use team keys
  • Rollout restart JupyterHub: oc rollout restart deployment/jupyterhub -n i3-ai-lab
curl -X POST https://litellm.i3technologies.co.ke/key/generate \
  -H "Authorization: Bearer sk-i3-internal" \
  -H "Content-Type: application/json" \
  -d '{"key_alias":"pilot-internal","max_budget":5.0,"rpm_limit":20,"duration":"180d"}'
2
Scale LiteLLM to 2 Replicas + Add JupyterHub Idle Culler
Removes single point of failure · prevents runaway notebook resource leak · ~30 min
  • Scale LiteLLM minimum replicas to 2 (HPA already allows up to 6)
  • Add idle culler: kill notebook servers after 60 min idle, hard kill after 24 h
oc patch deployment litellm-proxy -n i3-model-gateway \
  --type=merge -p '{"spec":{"replicas":2}}'

oc patch scaledobject keda-hpa-litellm-proxy-scaler \
  -n i3-model-gateway --type=merge \
  -p '{"spec":{"minReplicaCount":2}}'

Phase B — Deploy i3EduBridge + i3Social (Do After Phase A · ~4–6 hours)
5
Provision Databases in Shared PostgreSQL HA Cluster
Both i3EduBridge (Moodle) and i3Social (Nextcloud) share the existing Crunchy PG — no new DB pods needed · ~20 min
PGPOD=$(oc get pods -n i3-data \
  -l postgres-operator.crunchydata.com/role=primary \
  --no-headers -o custom-columns="NAME:.metadata.name" | head -1)

# Create i3EduBridge database
oc exec -n i3-data $PGPOD -- psql -U postgres -c \
  "CREATE USER edbridge_user WITH PASSWORD 'CHANGE_ME';
   CREATE DATABASE edbridge_db OWNER edbridge_user ENCODING 'UTF8';
   GRANT ALL PRIVILEGES ON DATABASE edbridge_db TO edbridge_user;"

# Create i3Social database
oc exec -n i3-data $PGPOD -- psql -U postgres -c \
  "CREATE USER social_user WITH PASSWORD 'CHANGE_ME';
   CREATE DATABASE social_db OWNER social_user ENCODING 'UTF8';
   GRANT ALL PRIVILEGES ON DATABASE social_db TO social_user;"
6
Deploy i3EduBridge — Namespace · Quota · PVC · Deployment · Service · Route
Moodle 4.4 · branded as "i3EduBridge" · shares Crunchy PostgreSQL · Keycloak OIDC SSO · ~30 min deploy + 10 min verify
  • Create namespace i3-edbridge with ResourceQuota: 1 CPU req / 2 GB RAM req / 4 CPU lim / 8 GB RAM lim
  • Create PVC edbridge-data: 10 GB on ibmc-vpc-block-10iops-tier
  • Deploy bitnami/moodle:4.4 — env: MOODLE_DATABASE_TYPE=pgsql, MOODLE_SITE_NAME=i3EduBridge, DB → shared PG cluster
  • CPU request: 500m · RAM request: 1 GB · CPU limit: 2 · RAM limit: 4 GB
  • Readiness probe: GET /login/index.php:8080 — initialDelaySeconds: 90 (Moodle first-boot install takes ~3–5 min)
  • Create ClusterIP Service on port 80 → container 8080
oc create route edge i3edbridge \
  --service=moodle --port=80 \
  --hostname=moodle.i3technologies.co.ke \
  --insecure-policy=Redirect -n i3-edbridge

Verify: https://moodle.i3technologies.co.ke/login/index.php returns HTTP 200 and shows "i3EduBridge" branding.

Deploy i3Social — Namespace · Quota · Redis · PVC · Deployment · Service · Route

  • Create namespace i3-social with ResourceQuota: 1 CPU req / 2 GB RAM req / 4 CPU lim / 8 GB RAM lim
