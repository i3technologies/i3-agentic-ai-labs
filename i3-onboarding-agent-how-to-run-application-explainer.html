1. What Is This Application?

The i3 Onboarding Agent is an AI-powered REST API that reads your real codebase and automatically generates a personalised, verified, 5-day ramp-up plan for any new team member joining your project.

You tell it the new hire's role (e.g. Platform Engineer). It reads the actual files in your repository, fires three AI subagents in parallel to analyse different parts of the codebase, checks that every file path it references actually exists, and produces a structured JSON plan with a Markdown document and Gantt chart — all in one API call.

🎯 The Problem It Solves

New hires waste their first week asking "where do I even start?" This agent reads the real codebase and answers that question automatically — with specific file paths, day-by-day tasks, and warnings when documentation is out of date.

🏆 The Hackathon Demo Moment

The platform docs say "RHOAI AI Lab available from Month 3" — but the namespace doesn't exist yet. The agent detects this live, flags the task as verified: false, and prefixes it with "Needs verification:" automatically.

Think of it as: a senior engineer who has read every file in your codebase, and can write a personalised onboarding guide for any new hire in under 30 seconds.

3. Request Lifecycle — Step by Step

Here is exactly what happens when you call POST /api/onboarding/plan with {"role": "platform_engineer"}:

1Lobster Trap Firewall

The request body fields (role, note) are scanned against 12 regex patterns for prompt injection. If any match — e.g. "ignore all previous instructions" — the request is rejected immediately with HTTP 400. The LLM is never called.

2Authentication Check

In production: the Bearer JWT is validated against Keycloak's JWKS endpoint using RS256. On your laptop with DEV_BYPASS_AUTH=true, a fake user (dev@localhost with i3-admin role) is injected automatically — no token needed.

3Skills Assessor — 3 Subagents Fire in Parallel

The role is looked up in the scan-plan table. For platform_engineer, three subagents are selected: infra-scan, ailab-scan, and backend-scan. All three run simultaneously using Promise.all().

Each subagent independently:

  1. Queries ChromaDB for relevant chunks (e.g. infra-scan asks for "ArgoCD Tekton ROKS namespaces")
  2. Builds a prompt combining the retrieved context + its focus areas
  3. Calls the LiteLLM gateway using the mistral-nemo (Tier 2) model
  4. Parses the JSON response with Zod validation to get a list of findings
4Verification Pass

Every file path in every finding is checked with existsSync() against the real platform/ directory. Two special checks also run:

  • RHOAI namespace check: If a finding mentions i3-ai-lab or RHOAI, the agent calls the live Kubernetes API to confirm whether that namespace exists. On your laptop (no cluster credentials), it conservatively assumes it does not — matching reality.
  • Any finding with missing paths → verified: false, title prefixed with "Needs verification: [title] (referenced path not found — likely stale doc)"
5Plan Synthesis — granite-heavy (Tier 1)

All verified findings are formatted into a summary and sent to granite-heavy (the most powerful model, Tier 1). The model produces 12–15 structured tasks spanning Days 1–5. A confidence gate of 0.65 filters out any task the model is less than 65% confident about. A deterministic fallback runs if the LLM fails.

6Store & Respond

The plan is stored in-memory with a planId like platform_engineer-1748500000000. The Markdown and Gantt chart are pre-rendered and cached. The API response includes the full plan JSON plus summary counts.

4. Every Module Explained

Security Layer

FileWhat It DoesWhen It Runs
security/lobster-trap.ts12 regex patterns that block prompt injection. Examples: "ignore all previous instructions", "you are now DAN mode", "DROP TABLE", "SELECT * FROM". Returns the matched pattern string, or null if clean.Before every protected endpoint, on the request body fields.
security/keycloak-auth.tsValidates Bearer JWTs using the Keycloak JWKS endpoint (RS256). Attaches req.user = {sub, email, roles[]} on success. Has a DEV_BYPASS_AUTH=true escape hatch for local development.After Lobster Trap, on every protected endpoint.

Ingestion Layer

FileWhat It Does
ingestion/types.tsDefines RawArtifact — the common shape every ingestion connector produces. Has source, sourceType, path, filePath, content, title, updatedAt. The makeArtifact() helper ensures both path aliases are always in sync.
ingestion/platform.tsWalks the entire platform/ directory, reads every .md .yaml .py .ts .tf .sql .json file under 256KB, skips solution-01..08 dirs, classifies each file as platform-doc or platform-code, and returns a list of RawArtifacts.
ingestion/github.tsUses the GitHub API (Octokit) to pull README files, Architecture Decision Records, and closed issues from any repo. Closed issues are valuable as "historical bug" references for onboarding tasks.
ingestion/curriculum.tsFetches the programme_guides collection from Directus CMS. Gracefully skips if Directus is unreachable (returns empty array). Used by the bootcamp_student role.
ingestion/evalos.tsFetches exam domain weights from the EvalOS API. If EvalOS is unreachable, falls back to hardcoded C1000-207 IBM certification exam domains (Agent Integration = 23 questions = 38% of exam).

Context Store Layer

FileWhat It Does
context-store/chroma-client.tsThin wrapper around ChromaDB. Creates/reuses a collection called onboarding-corpus. The embedding function routes through LiteLLM (granite-nano) so you never call OpenAI directly.
context-store/chunker.tsConverts RawArtifacts into small chunks suitable for vector search. Markdown files are split on headings; code files on 60-line blocks; SQL on semicolons; YAML on key blocks. Each chunk gets a deterministic ID and a role_tags metadata field based on keywords.
context-store/index.tsBatch-upserts chunks into ChromaDB in groups of 200. Idempotent — safe to run multiple times. The /api/onboarding/ingest endpoint calls this.
context-store/retriever.tsRuns HNSW cosine similarity search against ChromaDB. Accepts a query string + optional role tag filter. Returns the top-K most relevant chunks. Used by every subagent to get its context before calling the LLM.

Orchestrator Layer

FileWhat It Does
orchestrator/subagents/types.tsShared TypeScript types: OnboardingRole, SubagentFinding (the findings each subagent returns), SubagentInput (what each subagent receives).
orchestrator/subagents/base-scan.tsAbstract class all subagents extend. Handles the LiteLLM call (mistral-nemo), strips markdown fences from the response, validates JSON with Zod, and retries up to 2 times.
orchestrator/subagents/evalos-scan.tsSpecialises in EvalOS: database schema, Bloom taxonomy, C1000-207 exam domains, anti-cheat recording, n8n enrolment. Used for bootcamp_student.
orchestrator/subagents/ailab-scan.tsSpecialises in LLM infrastructure: LiteLLM tiers, ChromaDB, Lobster Trap, MCP connectors. Has a special instruction: if context mentions RHOAI without confirmed namespace, emit a historicalIssueRef: "stale-doc" finding at high priority.
orchestrator/subagents/infra-scan.tsSpecialises in cluster operations: ArgoCD waves, Tekton pipeline, OpenBao secrets, forbidden namespaces. Finding #1 is always the solution-01..08 forbidden rule.
orchestrator/subagents/backend-scan.tsSpecialises in API patterns: FastAPI structure, EvalOS schema, JWT authentication, OpenBao env-var conventions.
orchestrator/subagents/model-scan.tsSpecialises in LLM evaluation: RAGAS framework, promptfoo red-team, confidence gate tuning, Locust load tests.
orchestrator/skills-assessor.tsMaps each role to exactly 3 subagents. Fires all 3 in parallel using Promise.all(). Each subagent fetches its own RAG context first, then runs its scan. Returns all findings combined.
orchestrator/verify.tsLoops through every finding. Calls existsSync() on each referenced file path. Also calls the Kubernetes API to check if the i3-ai-lab namespace is live. Anything that fails gets verified: false and the stale-doc prefix on its title.
orchestrator/planner.tsTakes all verified findings and calls granite-heavy (Tier 1) to synthesise a 12–15 task, 5-day plan. Validates output with Zod. Drops tasks below the 0.65 confidence gate. Falls back to a deterministic plan builder if the LLM fails.

Render Layer

FileWhat It Does
render/markdownPlan.tsConverts a RampUpPlan into a readable Markdown document. Includes: header with timestamp, stale-doc warnings block, architectural summary table, 5 day-themed sections, per-task priority badges, historical issue callouts, and confidence percentages.
render/graph.tsTwo outputs: (1) a Mermaid Gantt chart with days as sections and tasks sized by estimated hours; (2) a static service topology diagram showing all 11 i3 platform services and how they connect.
render/taskSync.tsImplements the 2-stage CRM sync gate. Stage 1 generates a UUID token and previews the first 5 tasks. Stage 2 (after the user clicks Confirm) writes each task to Directus and fires the n8n webhook. Token expires after 5 minutes.

Entry Point

FileWhat It Does
server.tsThe Express application. Sets up the middleware chain (JSON parsing → request logging → Lobster Trap → Keycloak auth). Registers all 10 routes. Holds the in-memory plan store (Map). Starts listening on port 3000.

7. Running the Application

You need three terminal windows open simultaneously. Open them now, then follow each tab's instruction.

1TAB 1 Start the Mock LiteLLM Server

This replaces the real AI gateway. It returns realistic canned responses so the full pipeline works without cluster access.

cd onboarding-agent
node scripts/mock-litellm.mjs

Expected output:

[mock-litellm] listening on http://localhost:4000
[mock-litellm] models: granite-nano (Tier3), mistral-nemo (Tier2), granite-heavy (Tier1)
[mock-litellm] POST /v1/chat/completions → canned findings/plan responses
Leave this terminal running. It must stay alive for the agent to generate plans.
2TAB 2 Start ChromaDB (Vector Database)

This is the memory store that holds the platform repo chunks for semantic search.

cd onboarding-agent
npx --yes chromadb@latest

Application startup complete.
Uvicorn running on http://0.0.0.0:8000

8. Using the Application

Option A — PowerShell (recommended, already on your machine)

Open a new PowerShell window (Tab 4 can be reused after ingest is done) and run these commands:

Check the server is alive

Invoke-RestMethod http://localhost:3000/health

Check ChromaDB is connected and has data

Invoke-RestMethod http://localhost:3000/ready
# Expected: { status: "ready", chromadb: true }
# If chromadb: false — Tab 2 (ChromaDB) isn't running

Generate your first onboarding plan

$result = Invoke-RestMethod http://localhost:3000/api/onboarding/plan `
  -Method POST `
  -ContentType "application/json" `
  -Body '{"role":"platform_engineer"}'

# See the summary
Write-Host "Plan ID: $($result.planId)"
Write-Host "Total tasks: $($result.plan.tasks.Count)"
Write-Host "Verified: $($result.totalVerified)"
Write-Host "Needs verification: $($result.totalUnverified)"

# Show all tasks as a table
$result.plan.tasks | Format-Table day, priority, verified, title -Wrap

Read the Markdown plan (the pretty version)

$planId = $result.planId
$md = Invoke-RestMethod "http://localhost:3000/api/onboarding/plan/$planId/markdown"

# Print it directly
$md

# OR save to file and open in VS Code
$md | Out-File "my-onboarding-plan.md"
code my-onboarding-plan.md

View the Mermaid Gantt chart

$gantt = Invoke-RestMethod "http://localhost:3000/api/onboarding/plan/$planId/gantt"
$gantt

9. Full API Reference

Base URL: http://localhost:3000  ·  All /api/ routes pass through Lobster Trap + auth middleware (bypassed locally)

MethodEndpointGateDescription
GET /health — Liveness probe. No auth. Always returns {status:"ok"}
GET /ready — Readiness probe. No auth. Returns 200 if ChromaDB is reachable, 503 otherwise.
POST /api/onboarding/plan 🟢 AUTO Generate a ramp-up plan. Body: {"role":"platform_engineer"}. Valid roles: platform_engineer, ai_ml_engineer, bootcamp_student, backend_engineer, security_engineer. Optional: "note":"any context".
GET /api/onboarding/plan/:planId 🟢 AUTO Retrieve a stored plan as JSON. Returns 404 if planId not found.
GET /api/onboarding/plan/:planId/markdown 🟢 AUTO Retrieve the plan as a formatted Markdown document. Content-Type: text/markdown.
GET /api/onboarding/plan/:planId/gantt 🟢 AUTO Mermaid Gantt chart string. Paste into mermaid.live to visualise.
GET /api/onboarding/graph 🟢 AUTO Static Mermaid flowchart of the entire i3 platform service topology (11 services).
POST /api/onboarding/sync/prepare 🟡 ONE-CLICK Stage 1 of CRM sync. Body: {"planId":"..."}. Returns a pendingId token valid for 5 minutes and a preview of the first 5 tasks.
POST /api/onboarding/sync/confirm/:pendingId 🟡 ONE-CLICK Stage 2: user confirms. Writes tasks to Directus CRM and fires n8n webhook. Returns {success, syncedCount, skippedCount, directusIds[]}.
DEL /api/onboarding/sync/:pendingId 🟢 AUTO Cancel a pending sync (user clicked Dismiss). Returns {cancelled:true}.
POST /api/onboarding/ingest 🔴 ADMIN Re-index the platform corpus into ChromaDB. Requires Keycloak role i3-admin (auto-granted by DEV_BYPASS_AUTH). Returns IndexResult stats.
GET /api/onboarding/status 🟢 AUTO System status: ChromaDB health + chunk count, number of cached plans, pending sync count, active model aliases.

The Stale-Doc Detection — What to Look For

This is the primary demo moment. Look for tasks where:

  • verified: false
  • Title starts with: "Needs verification: … (referenced path not found — likely stale doc)"
  • verificationNote says: "RHOAI/i3-ai-lab namespace not live — platform-documentation.md states 'available from Month 3'"

This proves the agent is doing live verification, not just copying documentation blindly.

12. Troubleshooting

SymptomCauseFix
EADDRINUSE :3000 Another process is using port 3000 Add PORT=3001 to your .env and restart the agent
/ready returns chromadb: false Tab 2 (ChromaDB) is not running Start npx --yes chromadb@latest in a new tab, wait for "Application startup complete"
totalTasks: 0 in plan Tab 1 (mock LiteLLM) is not running Start node scripts/mock-litellm.mjs in Tab 1
HTTP 401 on API calls DEV_BYPASS_AUTH=true not in .env Run copy .env.local .env to restore the dev config
HTTP 400 "Request blocked by security policy" Your test input matched a Lobster Trap pattern This is correct behaviour — the injection was blocked. Use a clean input.
npm run dev fails with TypeScript error A code change introduced a type error Run npm run typecheck to see the exact error, fix it, then retry.
ChromaDB takes a long time to start First-time download of the chromadb package (~200MB) Wait for "Application startup complete" — subsequent starts are instant.
totalUnverified: 0 — no stale docs detected Mock LiteLLM isn't returning the RHOAI finding Check that Tab 1 is running; the mock always includes the RHOAI stale-doc task in its response.
Ingest produces 0 artifacts PLATFORM_REPO_PATH points to wrong directory Confirm PLATFORM_REPO_PATH=../platform in .env and that the platform/ folder exists one level up from onboarding-agent/.
