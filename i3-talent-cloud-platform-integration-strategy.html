i3 Talent Cloud — Platform Integration Strategy

Based on: i3 Talent Cloud Strategy & Technical Specification (September 2026)  ·  Target platform: IBM ROKS Frankfurt — OpenShift 4.17  ·  Reviewed by IBM Bob
Core finding: i3 Talent Cloud is not a greenfield build. Every infrastructure component it requires — Keycloak, LiteLLM, PostgreSQL, ChromaDB, SeaweedFS, Kafka, Langfuse, n8n, Directus — is already running in production on the i3 Master AI Platform. This is a productisation exercise on existing infrastructure, not a new platform build. Estimated new engineering is one new namespace family (i3-talent) and three new Next.js/FastAPI applications.

1. Document Summary — What i3 Talent Cloud Defines

The specification defines a Talent-as-a-Service (TaaS) business built on three linked offerings:

OfferingWhat it isRevenue model
i3 Talent Cloud Bench of vetted, EvalOS-assessed consultants available to clients on flexible engagements Monthly subscription bench access · day-rates
FDE Programme i3 Academy graduates embedded at client sites as Forward Deployed Engineers (min. Senior Practitioner score on EvalOS) FDE day-rate · retainer
i3 Recruit Head-hunting & placement agency for AI talent — draws on the same Talent Graph and EvalOS pipeline Placement fee (% of salary) · retained search · EvalOS-as-a-Service licences

The technical centrepiece is the Talent Graph — a typed-relationship store (nodes: Candidate, Certification, Skill, Assessment Event, Project Engagement, Client, Team; edges: holds-certification, scored-on, deployed-to, rated-by, mentored-by) — and a Talent Digital Passport per person (identity, certifications, risk tier, EvalOS scores, NDAs, expiry dates).

3. Proposed Integration Architecture

New namespace: i3-talent

Deploy Talent Cloud as a single new namespace following the exact same pattern as i3-engage, i3-pmaas, and i3-smartlab:

Workloads in i3-talent

  • talent-web — Next.js 14 portal (candidates, clients, recruiters, FDE dashboard)
  • talent-api — FastAPI — Talent Graph CRUD, Passport API, bench matching
  • talent-agent — AI coworker (bench matcher, JD analyser, score interpreter)

New DNS / Routes needed

  • talent.i3technologies.co.ke — candidate & client portal
  • recruit.i3technologies.co.ke — i3 Recruit public-facing job board
  • api.talent.i3technologies.co.ke — Talent Graph API

Data flow: Talent Graph on PostgreSQL

The Talent Graph lives in a new talent_db database on the existing Crunchy PostgreSQL cluster (PGBouncer endpoint: i3-postgres-pgbouncer.i3-data.svc:5432). No new database server is needed. Schema:

6. Key Integration Suggestions & Observations

Suggestion 1 — Start with EvalOS-as-a-Service (fastest revenue path)

The document itself recommends this: "Productise EvalOS first — package the existing assessment and Zuri AI capability as a standalone, sellable service within 60–90 days." EvalOS is already live at evalos.i3technologies.co.ke. The only addition needed is a client-facing Keycloak realm or tenant, an API token for external assessment invites, and a results webhook. This can be done in under a week on existing infrastructure — zero new namespaces.

Suggestion 2 — Use PostgreSQL JSONB for the Talent Graph, not a graph database

The document implies a graph database for the Talent Graph. However, given the existing Crunchy PostgreSQL HA cluster, JSONB + recursive CTEs handles the required node/edge queries at this scale (hundreds of candidates, not millions). Adding a new graph database (Neo4j, etc.) introduces unnecessary operational overhead. Use PostgreSQL with a well-indexed adjacency table: talent_edges(from_id UUID, to_id UUID, edge_type TEXT, metadata JSONB, valid_from TIMESTAMPTZ, valid_to TIMESTAMPTZ). Revisit only if the graph exceeds 50k nodes.

Suggestion 3 — Kafka topics for score decay are critical to implement correctly

The score decay model (skills depreciate if not refreshed) is one of the document's strongest differentiators. Implement it as a scheduled n8n workflow that daily queries skill_scores WHERE last_refreshed < NOW() - decay_window and emits talent.score-updates Kafka events. Kafka already runs in i3-messaging — this is zero-infrastructure-cost. Do not implement decay as a nightly cron job that mutates the database directly; the event log is the audit trail the governance section requires.

Suggestion 4 — Langfuse trace IDs on every AI evaluation decision are non-negotiable

Section 10 (Governance) states "no placement or deployment should be confirmed by AI recommendation alone — human approval stays in the loop." This requires a full audit trail of every LLM call made during evaluation. Every Talent Agent and Zuri AI invocation must pass X-LF-Session-Id headers to Langfuse and store the returned trace ID in the assessment_events table. Without this, governance compliance cannot be demonstrated to enterprise clients. Langfuse is already running in i3-ott — this is a configuration change, not infrastructure work.

Suggestion 5 — Use Engage for all candidate/client communications (already built)

Engage was just deployed with AI-personalised email, SMS (Africa's Talking), and a contact lists model. The Talent Cloud candidate communications described in the document — shortlist delivery emails, score expiry reminders, FDE onboarding confirmations, client feedback requests — map directly to Engage campaigns and contacts. Add candidates to an Engage contact list tagged talent-cloud and trigger campaigns via the /api/campaigns/send endpoint. No new messaging infrastructure needed.

Suggestion 6 — The Talent Digital Passport should be a verifiable OpenBadge

The document defines the Talent Digital Passport as a machine-readable object. Consider extending it to an Open Badges 3.0 verifiable credential signed by i3's own key (stored in OpenBao). This makes the passport portable and externally verifiable — a candidate can share their passport URL with any employer and have it cryptographically verified against i3's public key. This directly supports the "defensible technical moat" the document claims.

Suggestion 7 — DNS records to add at cPanel

Three new CNAME records will be needed (all pointing to 8eec2322-eu-de.lb.appdomain.cloud):

  • talent → i3technologies.co.ke
  • recruit → i3technologies.co.ke
  • api.talent → i3technologies.co.ke (requires a new LE cert via acme-dns, same pattern as SmartLab)

7. Gaps in the Specification (Items to Address Before Build)

GapRecommendation
No data model for the Talent Graph is specified Define the PostgreSQL schema before any code is written — all three offerings (bench, FDE, recruit) must write to the same schema or they become silos
Multi-tenancy model not defined — single Keycloak realm or per-client tenant? Use a single i3 realm with role-based scoping for MVP. Per-client tenants (separate realms) only needed if clients require data isolation at the identity layer — deferred to Phase 3
EvalOS API contract not specified — does it expose REST endpoints for external score ingestion? Add a /api/results/webhook endpoint to evalos-web that accepts a signed POST from the Talent API and writes to assessment_events. n8n handles the fan-out
Score decay window values not defined per skill track Define decay windows in a Directus CMS content type so non-technical staff can adjust them without code changes (e.g. IBM watsonx cert: 12-month decay; soft skills: 24-month; live coding: 6-month)
No mention of GDPR / Kenya Data Protection Act 2019 compliance for CV and personal data storage All PII stored in SeaweedFS and PostgreSQL. Implement a right-to-erasure endpoint in the Talent API that hard-deletes candidate records on request. OpenBao already handles secrets — extend to store data encryption keys per candidate for field-level encryption of sensitive passport fields
Client portal access model unclear — do clients get SSO accounts or token-based access? Issue clients a Keycloak account with role talent-client for the shortlist review portal. Use short-lived signed URLs (from Talent API) for one-time shortlist sharing that doesn't require account creation

Summary

The i3 Talent Cloud specification is well-aligned with the existing platform and technically sound. The main integration recommendation is: build thin on top of what exists. The Talent Graph API and portal are the only genuinely new applications. Everything else — identity, AI inference, assessment, notifications, workflows, storage, observability — is already running in production and needs only configuration and connection.

The fastest path to commercial value is to productise EvalOS as a standalone assessment service (already live, needs only a client-facing access model) within 60 days, then build the Talent Graph and portal over the following 8 weeks — exactly the sequence the document's own Board Recommendations propose.
