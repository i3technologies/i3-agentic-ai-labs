1. System Overview

The i3 Onboarding Agent is a production-grade, RAG-powered AI service that ingests the i3 Agentic AI Labs platform repository and generates verified, role-specific, 5-day ramp-up plans for new team members. It is deployed as namespace i3-onboarding on the live ROKS 4.15 cluster (Frankfurt, eu-de) as ArgoCD wave 7.

What it does

  • Ingests real platform repo files into ChromaDB
  • Fires 3 parallel subagents per role request
  • Verifies every file path against the live repo
  • Flags stale docs (verified: false)
  • Synthesises a 5-day JSON plan via granite-heavy
  • Renders Markdown + Mermaid Gantt output
  • Syncs tasks to Directus CRM (one-click gate)

What it does NOT do

  • Auto-write to EvalOS or Keycloak (🔴 blocked)
  • Touch solution-01…08 namespaces (hard constraint)
  • Accept requests without Keycloak JWT
  • Pass user input to LLM before Lobster Trap check
  • Store secrets in code or git (OpenBao only)
  • Call watsonx.ai for Tier 2/3 tasks (credit conservation)

4. Security Model

4.1 Lobster Trap — Prompt Injection Firewall

File: src/security/lobster-trap.ts · Ported from platform/admissions/admissions_agent.py

Applied pre-LLM on all user-supplied text fields (role, context, query, note) in every request body before any model call is made.

#PatternCatches
1/ignore\s+(all\s+)?previous\s+instructions?/iClassic injection opener
2/you\s+are\s+now\s+(?!an?\s+(onboarding|platform|i3))/iPersona hijack
3/act\s+as\s+(?!an?\s+(onboarding|platform|i3))/iRole override
4/system\s*(prompt|message|instruction)/iSystem prompt exfil
5/jailbreak/iJailbreak attempts
6/DAN\s+mode/iDAN jailbreak variant
7/<\s*(script|img|iframe|svg)/iHTML/XSS injection
8/(drop|delete|truncate)\s+table/iSQL DDL injection
9/SELECT\s+.+FROM\s+/iSQL exfiltration
10/prompt\s+injection/iSelf-referential injection
11/disregard\s+(all\s+)?previous/iInstruction override variant
12/\bexfiltrate\b/iData exfiltration intent

On match: HTTP 400 returned with { error: "Request blocked by security policy", pattern: "<matched>" }. No LLM call is made.

4.4 Secret Management

All secrets are injected at runtime from OpenBao KV v2 at path i3/onboarding-agent/ via vault-agent sidecar annotations on the Deployment. The openshift/deploy.yaml Secret manifest contains only empty placeholder values — actual values are never committed to git.

⛔ Never hardcode: LITELLM_KEY, CHROMA_TOKEN, DIRECTUS_TOKEN, EVALOS_API_KEY, GITHUB_TOKEN, KEYCLOAK_SECRET in any file. These must only exist in OpenBao.

8. Orchestrator: Verify & Plan

8.1 Verify (verify.ts)

File: src/orchestrator/verify.ts

Runs after all subagents complete. For every SubagentFinding:

  1. Calls existsSync(join(PLATFORM_REPO_PATH, filePath)) for each path
  2. Checks if finding mentions rhoai or i3-ai-lab, then calls live Kubernetes API (GET /api/v1/namespaces/i3-ai-lab) with SA token
  3. If any path missing OR RHOAI check fails → verified: false, title prefixed with "Needs verification: [title] (referenced path not found — likely stale doc)"
  4. RHOAI result is cached per process (lazy singleton)
Demo Proof-Point: platform/docs/platform-documentation.md states RHOAI (i3-ai-lab namespace) is "available from Month 3". The live Kubernetes API confirms it does not exist → verified: false is emitted automatically. This is the primary demo moment showing the agent catches stale documentation.

taskSync.ts — 2-Stage CRM Sync

File: src/render/taskSync.ts · Mirrors platform/admissions/mcp/mcp_connectors.py _pending pattern

  • Stage 1 (prepareSyncTasks): generates UUID pending token, stores in Map<string, PendingSync>, TTL 5 minutes, returns preview of first 5 tasks

  • Production note: replace in-memory _pending Map with Redis for multi-replica deployments

13. MCP Connector Extension

File: platform/admissions/mcp/mcp_connectors.py

Two new endpoints added to the existing FastAPI MCP Connector service, reusing the same in-memory _pending dict pattern and 2-stage confirmation gate:

POST /tools/onboarding/sync-tasks (Stage 1)

Body: SyncTasksRequest { role, user_id, tasks: OnboardingTask[] }

Returns: { requires_confirmation: true, token, task_count, preview: [{ day, title, priority }], summary }

Token TTL: 5 minutes. Stored in _pending dict with action: "onboarding_sync_tasks".

POST /tools/onboarding/confirm/{token} (Stage 2)

Validates token exists, action matches, TTL not expired. Writes each task to DIRECTUS_URL/items/onboarding_tasks with full field set. Fires N8N_ONBOARDING_WEBHOOK_URL (best-effort, 5s timeout). Returns { success, synced_count, skipped_count, directus_ids[] }.

Production Note: The _pending dict is in-memory. For multi-replica deployments of mcp_connectors, replace with Redis to avoid token-not-found errors across pod restarts.
