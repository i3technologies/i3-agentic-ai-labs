1 — Attack Surface Overview

Tenancy Enforcement Stack (deepest defence first) Layer 1 · Keycloak RS256 JWT — tenant_id claim baked at authentication boundary, signed with realm private key. No mutation possible post-issuance.
Layer 2 · Kong API Gateway — CORS + OIDC plugin validates Bearer token before it reaches any service. Unauthenticated requests rejected at network edge.
Layer 3 · NextAuth / FastAPI middleware — per-request JWT decode, issuer check, expiry check; tenant_id extracted and pinned to request context.
Layer 4 · MCP Gateway — X-Tenant-Id header cross-checked against agent manifest fetched from trusted Agent Registry (manifest.tenant_id ≠ header → HTTP 403).
Layer 5 · PostgreSQL RLS — SET LOCAL app.tenant_id executed before every query; 17 tables protected; policy USING (tenant_id = current_setting('app.tenant_id')::uuid).
Layer 6 · S3 WORM Audit Trail — every denied event written to append-only Object-Lock bucket; chained HMAC prevents post-write tampering; actor_id is HMAC-SHA256 (HC-6).

4 — Hardening Findings

F-01 MEDIUM Consent service accepts caller-supplied tenant_id without authentication (AT-09)

Finding: platform/consent/main.py trusts tenant_id as a query parameter and performs no caller-identity validation. Relies entirely on Kong upstream enforcement and network policy.

platform/consent/main.py — tenant_id: uuid.UUID = Query(..., description="HC-4 mandatory tenant scoping") # No requireAuth dependency present on GET /consent/{subject_id_hash}

Impact: In-cluster attacker who bypasses Kong could query any tenant's consent data by guessing a valid tenant UUID. RLS provides a second-layer defence, but attacker who supplies the correct UUID gets those rows.

Remediation: Add a Kong oidc plugin to the consent route, or implement an internal service-account token check. Alternatively, add a Network Policy restricting ingress to consent service from known service IPs only.

Owner: Platform Security · Deadline: Before Phase 3 go-live

F-02 MEDIUM JWT fallback to hardcoded tenant_id when claim is absent (multi-service)

Finding: Both admissions_agent.py and mcp_connectors.py fall back to a hardcoded default UUID when the tenant_id JWT claim is missing.

admissions_agent.py:112 — return payload.get("tenant_id") or FALLBACK_TENANT_ID # "00000000-0000-0000-0000-000000000001" mcp_connectors.py:124 — tenant_id = payload.get("tenant_id") or FALLBACK_TENANT # same pattern

Impact: A valid Keycloak token whose realm mapper is mis-configured (missing tenant_id claim) silently operates as the fallback tenant, potentially allowing unexpected data access for that tenant's rows.

Remediation: In multi-tenant production, replace or FALLBACK_TENANT_ID with an explicit reject:

tenant_id = payload.get("tenant_id") if not tenant_id: raise HTTPException(status_code=401, detail="tenant_id claim missing from JWT")

Owner: Platform Engineering · Deadline: Before Phase 3 go-live

F-03 LOW Tekton pipeline lacks explicit namespace whitelist parameter validation (AT-11)

Finding: platform/gitops/tekton/pipeline-build.yaml passes $(params.STAGING_NAMESPACE) directly to oc set image without validating against an allowed list. SA RBAC is the sole preventive control.

pipeline-build.yaml:257–262 oc set image deployment/$deploy app=$(params.IMAGE) -n $(params.STAGING_NAMESPACE) # No step validates that STAGING_NAMESPACE is in [i3-staging, i3-prod]

Impact: Attacker with PipelineRun creation rights could target arbitrary namespaces. Blocked by SA RBAC today; defence in depth recommends parameter validation as an additional layer.

Remediation: Add a validation step before deploy:

- name: validate-namespace image: bash:5.2 script: | ALLOWED="i3-staging i3-prod" if ! echo "$ALLOWED" | grep -qw "$(params.STAGING_NAMESPACE)"; then echo "FORBIDDEN namespace: $(params.STAGING_NAMESPACE)"; exit 1 fi

Owner: DevOps · Deadline: Phase 3 sprint
