4 DNS & Ingress Configuration

All public subdomains are CNAME records pointing to the IBM Cloud VPC Load Balancer FQDN: 8eec2322-eu-de.lb.appdomain.cloud (resolves to 149.81.239.32 and 158.176.12.150).

9 Storage Architecture

Object Storage (SeaweedFS)

SeaweedFS provides S3-compatible object storage at storage.i3technologies.co.ke. It consists of:

  • 1× Master node (i3-ott/seaweedfs-master-0) — retain PVC 20Gi
  • 3× Volume nodes (seaweedfs-volume-0/1/2) — retain PVC 100Gi each
  • 1× Filer (seaweedfs-filer) + S3 gateway (seaweedfs-s3-gw)

DR sync: nightly rclone CronJob (0 2 * * *) pushes SeaweedFS data to IBM COS bucket.

16 Security Hardening Reference

  • Zero-trust network model: All namespaces have deny-all-ingress NetworkPolicy. Only explicitly whitelisted sources can connect.
  • TLS everywhere: All public routes use TLS (edge or re-encrypt). HTTP traffic is auto-redirected to HTTPS by insecureEdgeTerminationPolicy: Redirect.
  • No shared master keys in apps: JupyterHub uses virtual key pilot-jupyterhub (not the LiteLLM master key). Each team has a scoped key with budget limits.
  • OIDC SSO enforced: All major apps authenticate through Keycloak i3 realm. Direct password login is disabled where possible.
  • Secrets in cluster only: No secret values in Git. All managed as Kubernetes Opaque secrets.
  • OpenBao HA: 3-node Raft HA, auto-unseal configured. Root token and unseal keys must be stored offline (not in cluster).
  • ResourceQuotas: All i3-* namespaces have ResourceQuota objects limiting CPU/memory/PVC. Prevents runaway pods from starving the cluster.
  • ImagePullSecrets: icr-pull-secret is set in namespaces that pull from IBM ICR. Docker Hub rate limits are handled by using pre-pulled images where possible.
  • SCC (Security Context Constraints): Pods run with restricted-v2 SCC by default. Only i3-edbridge and i3-social have anyuid granted to their default SA (required by Apache-based images).
  • Audit logging: OpenShift audit logs are enabled at the API server level (IBM ROKS managed).
